## 一、日常使用

### 1.1 可视化面板（Web / DSH Desktop）

重启后，会话右上角工具区会多出一个 **「围栏」** 按钮：

- 按钮上的数字 = 当前会话规则条数；旁边小圆点是启用状态（亮 = 已启用）。
- 点击打开浮层面板，可逐条查看 / 编辑 / 删除规则，切换启用状态，底部实时显示 `注入 N 字符 ≈ M token`。
- 所有改动**下一轮生效**，不需要重启。
- 面板只在该会话打开时渲染内容，关闭即零占位。

面板走宿主注册的 `POST/GET /api/dialog-fence` 路由（由 `connection.fetch` 提供，自带 Connection 层鉴权）。CLI / TUI / headless 没有 `connection` 服务，插件会静默跳过路由注册，`/fence` 命令照常可用。

### 1.2 斜杠命令（所有形态）

在**任意想加围栏的对话**里直接用斜杠命令（命令由插件注册，宿主内建 UI 会提示）：

| 命令 | 作用 |
|---|---|
| `/fence` | 查看本会话围栏状态（启用与否、规则条数、实际注入文本、token 估算） |
| `/fence on` / `/fence off` | 启用 / 停用本会话围栏 |
| `/fence add <规则文本>` | 追加一条规则（自动启用；重复文本不会重复添加） |
| `/fence rm <序号>` | 删除第 N 条 |
| `/fence clear` | 清空本会话规则（保留启用状态） |
| `/fence reset` | 彻底删除本会话记录 |
| `/fence help` | 帮助 |

要点：

- **规则永远只作用于当前会话**。`rules.json` 以 `sessionId` 为键分桶，没有登记的会话渲染空字符串 → 零注入、零 token。
- 规则改动**下一轮立即生效**，不需要重启。
- 单条 ≤ 400 字符；每会话最多 40 条 / 渲染 2400 字符封顶。
- 规则里**不要写 `{{ }}`**：宿主的 `interpolate()` 遇到未注册变量会抛错。插件已用 `try/catch` 兜底（降级为空），但内容会静默失效。

### 1.3 直接编辑 rules.json

文件：`harness/dialog-fence/rules.json`（`DIALOG_FENCE_RULES` 环境变量可改位置）

```json
{
  "version": 1,
  "sessions": {
    "session-<uuid>": {
      "enabled": true,
      "rules": ["规则一", "规则二"]
    }
  }
}
```

⚠ **必须用 UTF-8（无 BOM）写入**。历史事故见「变更记录 · 事故 1」。插件已做编码自动探测，但仍建议用编辑器或 `node` 写，不要用 PowerShell 的 `Set-Content` / `Out-File` / `>` 重定向。

## 二、怎么改插件代码

1. 编辑 `harness/dialog-fence/index.js`（宿主半边）或 `harness/dialog-fence/client.js`（浏览器半边）。
2. **必须重启 DSH Desktop 才生效**（实测：`dsh-hmr` 未重载本插件，见「变更记录 · 事故 2」）。client.js 同样需要重启 —— 浏览器 bundle 由 `dsh-client-modules` 在启动时按 graph 组装。
3. 改完先跑四个无宿主测试（不需要宿主，也**不碰线上 rules.json**）：

```powershell
$env:ELECTRON_RUN_AS_NODE="1"
$exe = "D:\DSH Desktop\DSH Desktop.exe"
$dir = "C:\Users\<你>\AppData\Roaming\dsh-desktop\harness\dialog-fence"
& $exe "$dir\test\smoke.mjs"
& $exe "$dir\test\route.mjs"
& $exe "$dir\test\client.mjs"
& $exe "$dir\test\render.mjs"
```

期望输出四行：

```
OK all dialog-fence smoke assertions passed
OK all dialog-fence route assertions passed
OK all dialog-fence client bundle assertions passed
OK all dialog-fence render assertions passed
```

四个测试各管一段：`smoke` = 宿主逻辑（隔离性/命令/上限/编码兼容）；`route` = HTTP API（GET/HEAD/POST、非法 sessionId、未知 action、405）；`client` = 浏览器 bundle 形态（`__ModuleLoader__.load`、`factory`、导出、无裸 `import`、`dsh.client` 解析链）；`render` = 用 DSH 自带的**真 React 18** 把头部按钮真渲染一遍（`react-dom/server` 的 `renderToStaticMarkup`），确认组件在真 hooks 运行时下不违规、首帧产出预期 DOM。`render` 只看首帧 —— `renderToStaticMarkup` 不执行 `useEffect`，「点开面板拉数据」仍需浏览器验证（见 1.1、2 的「验证面板是否真的挂上了」）。找不到真 React 时会打印 `SKIP dialog-fence render test` 并 exit 0。

测试通过 `DIALOG_FENCE_RULES` 把插件指向系统临时目录里的一次性沙箱，跑完自动删除，并在结尾断言线上文件一字未动。

### 临时停用 / 卸载

**方式一（推荐）：用安装器**

```powershell
node scripts/install.mjs uninstall      # 只删标记块，rules.json 保留
node scripts/install.mjs status         # 查当前状态
```

**方式二：手工编辑补丁层**

在 `harness/profiles/web/cordis.patch.yml` 里找 `- id: dialog-fence` 那个 insert 块：

```yaml
- insert:
    - id: dialog-fence
      name: "file:///C:/Users/%3C你%3E/AppData/Roaming/dsh-desktop/harness/dialog-fence/index.js"
```

- 临时停用：在 `name:` 同级加 `disabled: true`。
- 彻底卸载：删掉整个 `- insert:` 块（含上方注释）。`rules.json` 可保留，重新挂回即恢复。

### 验证面板是否真的挂上了

重启后在浏览器打开 DSH，看两处：

1. 会话右上角是否出现「围栏」按钮。没有 → 客户端 bundle 未被扫到，检查 `package.json` 的 `dsh.client` 与 `exports['./client']`。
2. 点开后 DevTools Network 里是否有 `api/dialog-fence?sessionId=...` 请求且返回 200。返回 401 → 宿主路由没注册（`connection` 服务缺失或插件没重启）；404 → `dsh.client` 声明没被 `dsh-client-modules` 接受。

## 三、排查手册

### 症状：围栏文本没出现在下一轮

按顺序查：

1. **会话 id 对不对** —— `/fence` 会打印当前 `sessionId`，与 `rules.json` 里的键逐字比对。
2. **enabled 是否为 true** —— `/fence status` 看状态行。
3. **文件编码** —— 用这条命令看首字节：
   ```powershell
   $b=[System.IO.File]::ReadAllBytes("C:\Users\<你>\AppData\Roaming\dsh-desktop\harness\dialog-fence\rules.json"); "$($b.Length) bytes, first: $($b[0]),$($b[1]),$($b[2])"
   ```
   - `123,34,118` = `{"v` → UTF-8 正常 ✔
   - `255,254,123,0` = UTF-16LE（旧代码会解析失败）
   - `239,187,191` = UTF-8 BOM（旧代码会解析失败）
4. **插件是否被加载** —— 重启后 startup 日志里搜 `dialog-fence`；插件本身只 `console.log` 一行 ready，不写 DSH 日志文件。

### 症状：改完 index.js 没生效

正常现象（当前版本）。**重启 DSH Desktop**。

### 症状：缓存命中率突然掉

用 `acp_cache` / `/acp-cache` 看归因。判定口诀：

- `divergence ... tail-append` 或 `tail(params/notes)` → 正常，前缀没坏。
- `mid-history` + `no fold/switch/restart attribution` → 先看 `bili.log` 里 `strict-echo: injected blank reasoning_content on N assistant tool-call message(s)`。这是 **billion-context 自己**在改写历史 assistant 消息，与围栏无关（见「变更记录 · 实测 3」）。
- `PROVIDER-SIDE MISS` / `UPSTREAM TTL EXPIRY` → 上游缓存过期或被驱逐，与本插件无关。

### 真要让围栏永不被压缩

编辑 `C:\Users\<你>\.config\billion-context\billion-context.json`：

```json
{ "compress": { "protectedTools": ["durable/*"] } }
```

代价：旧快照永不折叠，上下文单调增长。默认**不建议**。

### 事故 1（已修复，需重启生效）：PowerShell 写坏 rules.json → 围栏静默消失

**经过**：用 `$state | ConvertTo-Json | [System.IO.File]::WriteAllText(...)` 写 `rules.json`，中文被按 GBK/UTF-16 落盘。插件 `JSON.parse` 抛错 → 被最外层 `catch` 吞掉 → 返回空串 → 围栏无声消失，无任何报错。

**修复**：`loadState()` 改为读 Buffer 后自动探测编码（含 `\u0000` 判定 UTF-16LE），并去掉 BOM；解析失败时 `console.warn` 一次（按 mtime+size 去重，不会刷屏）。

**回归**：`test/smoke.mjs` 新增两条断言 —— 把 `rules.json` 改写成「UTF-8 带 BOM」和「UTF-16LE」后，围栏必须仍能渲染。

**附带的隔离修复**：冒烟测试原先直接读写线上 `rules.json`，测试中途崩溃就会弄丢真实规则。现改为设置 `DIALOG_FENCE_RULES` 环境变量，把插件指向系统临时目录中新 `mkdtemp` 的一次性沙箱；测试结尾断言沙箱已删、线上文件未被写脏。

**状态**：代码已改，冒烟测试通过；**但运行中的实例仍是旧代码**（见事故 2）。

### 事故 2（已知限制）：`dsh-hmr` 不重载本插件

**实测证据**：编辑 `index.js` 加入 UTF-16LE 兼容后，把 `rules.json` 写成 UTF-16LE —— 若新代码生效，围栏应显示 `HMRTEST` 规则；实际快照里**围栏整段消失**，说明运行的仍是旧代码（旧代码无法解析 UTF-16LE）。触摸文件时间戳后再试一次，结果相同。

**结论**：改插件代码必须重启 DSH Desktop。`cordis.patch.yml` 里那行 `hot reloads via dsh-hmr` 注释对本插件不成立。

**注意**：这意味着**事故 1 的编码修复当前尚未生效**。在重启之前，`rules.json` 必须保持 UTF-8 无 BOM。

### 实测 3：单变量缓存实验（围栏改动不破坏前缀缓存）

在其余条件不变的前提下，向 `rules.json` 追加一条规则后立刻观测下一次真实请求：

```
#484  10:31:23  input=111.5K  cached=108.4K  hit 97.2%  new=2729  comp=0  ttl=337
```

`ttl=337` 是本次唯一可归因于「围栏文本变化」的 re-bill 量，`new=2729` 是正常的新增对话内容。**围栏改动 ≈ 追加 337 token，不产生前缀重写。**

对照：同期两条 `[cache-seam] mid-history` 告警（`#408` message[3]、`#478` message[46]）与围栏文本变化时刻重合，但根因是 billion-context 自己的 strict-echo 改写：

```
02:28:31 strict-echo: injected blank reasoning_content on 3 assistant tool-call message(s)
02:29:38 ... on 5 ...
02:30:34 ... on 6 ...
```

它不断往**历史 assistant 消息**里补空 `reasoning_content`，每补一条就产生一次 mid-history 偏移；`BODY STABILITY` 统计的 25 次 mid-history divergence 即由此而来。围栏注入发生在消息数组**尾部**，不可能是 message[3] / message[46] 的成因。

另外，`bili.log.old` 里在插件存在**之前**就有 9 条同类 cache-seam（跨 2026-09-30 ~ 10-15 的多个历史会话），进一步排除本插件。

**总账**：本会话 484 次请求，命中率 **95.7%**，折叠净收益 +233.99M token。
