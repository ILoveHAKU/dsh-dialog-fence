## 一、日常使用 / Day-to-day use

### 1.0 界面一览

| 界面 | 位置 | 管什么 |
|---|---|---|
| **设置页** | 设置左栏 → 「对话围栏」 | **主入口**：总开关 + **通用规则的直接编辑**（逐条内联改 / 增 / 删 / 清空）+ **某个对话的专属规则**（下拉选对话，默认选中当前对话；可单独停用该对话）+ **打开文件夹 / 更改位置** |
| **插件详情页配置区** | 左侧「插件」→ **已安装** → dsh-dialog-fence → 详情页（包描述与行之间） | 同一份界面 |
| 会话按钮 | 会话右上角工具区「围栏」+ 条数徽标（两层合计） | 打开**本会话**规则浮层 |
| 规则浮层 | 右下角面板（宽 480px，**点外部自动关闭**） | **与设置页同一套四张卡片**（紧凑版）：总开关 + 通用规则编辑 + **任意对话的专属规则（下拉默认停在那条对话）** + 打开文件夹；另加顶部标题与「关闭」 |
| 插件页标签页 | 设置 → 内置插件 → 「对话围栏」 | 同一份界面（老入口） |

五处界面写的是同一个围栏文件：改完 → 落盘 → 下一轮装配时重新读 → 生效。没有状态分叉。

> 0.5.0 起本插件按**组合包**安装，所以卡片在「**已安装**」分组（不再是「官方」分组）；
> 配置区通过 `plugins.bundle.config` 槽位（key = 包名 `dsh-dialog-fence`）渲染在该包详情页里。
>
> 0.6.0 起设置页**不再展示 sessionId 表**（用户 CR-12：「展示 sessionId 没有意义」），
> 改成直接编辑通用规则正文。
>
> 0.7.0 按用户 CR-14 三条改：①会话头部面板**同步显示通用规则**（以前只显示会话层，
> 于是刚配好的 10 条通用规则在浮层里看不到）②新增**打开文件夹 / 更改位置** ③存储从
> 「一条规则一个 txt」改为**单个 `fence.json`**。
>
> 0.10.0 起设置页第三张卡不再是「一句话让你去点浮层」，而是和浮层下半部分**完全一致**的编辑区
> （下拉选对话 + 规则列表 + 新建框 + 清空）。下拉里显示**对话名称**、默认选中**当前对话**、
> 任何情况下都不显示 `session-<uuid>`。浮层同时支持**点击外部关闭**。
>
> **0.12.0 起浮层不再有自己的实现**：它直接渲染设置页那四张卡片（紧凑版式），只在外面套一层
> 标题 + 总开关状态 + 「关闭」。于是浮层里也能选**任意对话**改专属规则（下拉默认停在你点开的那条），
> 两处的分区/文案/按钮从此由**同一份代码**决定（`client.js` 净减约 110 行重复实现）。
> 设置页也补上了「停用该对话 / 启用该对话」——此前这个动作只有浮层有。

### 1.1 可视化面板（Web / DSH Desktop）

重启后，**设置左栏 → 「对话围栏」** 就是主编辑入口（对每个对话生效的通用规则）：

- 顶部：总开关 pill + 「关闭围栏 / 开启围栏」按钮 + 一句说明 + **围栏文件完整路径** +
  「打开文件夹」「更改位置」两个按钮（0.7.0）。
- 每条通用规则占一行：序号 + 正文 + 「改」「删」 + **启停滑块**（最右端；滑块 0.13.0 起）。
- 点「改」把该行就地变成**多行编辑框**（0.9.0 起），`Ctrl+Enter` 保存 / `Esc` 取消 —— `Enter` 现在是换行。
- 底部多行编辑框新建一条，旁边「清空全部」；末尾实时显示
  `注入 N 字符 ≈ M token · K/40 条 · 单条上限 2000 字符`。
- 再往下是 **「某个对话的额外规则」**（0.10.0 起）：下拉里按名称选对话，默认已经选中**当前对话**，
  下面就是那个对话的专属规则（逐条「改」「删」）+ 新建框 + 「添加专属规则」/「清空该对话的专属规则」。
  下拉选项**只显示名称**（重命名过的用你起的名字，否则项目目录名，都没有则「未命名对话 N」），
  当前对话后面标「（当前）」；`<option>` 的 value 用数组下标，所以 DOM 里不会出现 `session-<uuid>`。
- 再往下是 **「不使用围栏规则的对话（可选）」**（0.14.0 起）：一列可滚动的复选行，勾上的对话
  **整段跳过围栏**（通用 + 专属都不注入），规则一条都不删，取消勾选立刻恢复。默认一条都不勾。
  列表里的名字单行省略，勾选框 / 标记 / 底部「全部不使用围栏」「恢复全部使用围栏」两个按钮都不可收缩，
  所以勾再多条只让这一列自己纵向滚动，横向布局不动（这正是用户要求的「不要多选了以后把别的东西挤出去」）。
- 所有改动**下一轮生效**，不需要重启。

会话头部那个 **「围栏」** 按钮打开的面板与**设置页是同一套四张卡片**（0.12.0 起）：

- 按钮上的数字 = 通用规则数 + 本会话专属规则数；高亮（`data-on="true"`）= 本会话已启用。
- 面板里面就是设置页那四张卡（紧凑版式），只在外面多一层标题 + 总开关状态 + 「关闭」。
  打开浮层即重新拉一次本会话、通用层与概览，所以设置页刚改过的内容立刻可见 —— 两个入口写同一个 `fence.json`。
- 面板里的**对话下拉默认停在你点开的这条对话**（`preferredSessionId`），所以浮层里也能改**任意对话**的专属规则；
  即使 `sessions` store 还没拉到数据，那条对话也会以「当前对话」出现在候选里，不会出现「点开却选不到自己」。
- **点浮层外部任意位置即可关闭**（0.10.0 起）：监听 `document` 的 `mousedown` 捕获阶段，判断落点是否在 `.dialog-fence-panel` 或 `.dialog-fence-trigger` 内；点在右上角那个「围栏」按钮上**不算外部**，否则「点按钮关闭 → 按钮 onClick 又打开」会互相打架。

面板与三处配置页都走宿主注册的 `GET/HEAD/POST /api/dialog-fence` 路由（由 `connection.fetch` 提供，自带 Connection 层鉴权）。通用规则用 `?scope=common` / `{scope:'common'}`，不需要 sessionId；`openFolder` / `setFile` / `toggleGlobal` / `switch` 同样不需要。CLI / TUI / headless 没有 `connection` 服务，插件会静默跳过路由注册，`/fence` 命令照常可用。

### 1.2 斜杠命令（所有形态）

在**任意想加围栏的对话**里直接用斜杠命令（命令由插件注册，宿主内建 UI 会提示）：

| 命令 | 作用 |
|---|---|
| `/fence` | 查看本会话围栏状态（启用与否、两层条数、实际注入文本、token 估算） |
| `/fence on` / `/fence off` | 启用 / 停用本会话专属规则（不影响通用规则）；**带序号则只动那一条**（`/fence off 2`，0.13.0 起） |
| `/fence add <规则文本>` | 追加一条**本会话**规则（默认启用；重复文本不会重复添加） |
| `/fence rm <序号>` | 删除本会话第 N 条（序号从 1 开始，按注入顺序） |
| `/fence clear` | 清空本会话规则（保留启用状态） |
| `/fence reset` | 彻底删除本会话记录 |
| **`/fence mute`** / **`/fence unmute`** | 本会话整段不使用围栏（通用 + 专属都不注入）/ 恢复使用；带会话 id 则操作指定会话（0.14.0 起） |
| **`/fence muted`** | 列出所有「不使用围栏」的会话（0.14.0 起） |
| `/fence dir` | 打印围栏文件路径与所在目录 |
| `/fence open` | 打开围栏文件所在文件夹 |
| `/fence file <绝对路径>` | 把围栏文件迁移到指定位置（必须绝对路径、`.json` 结尾；原文件保留） |
| `/fence switch on` / `/fence switch off` | 总开关（两层一起开/关） |
| **`/fence all`** | 查看**通用规则**（对每个对话都生效） |
| **`/fence all add <规则文本>`** | 追加一条通用规则（默认启用） |
| **`/fence all rm <序号>`** | 删除第 N 条通用规则 |
| **`/fence all on <序号>` / `all off <序号>`** | 启用 / 停用第 N 条**通用规则**（0.13.0 起） |
| **`/fence all clear`** | 清空通用规则 |
| `/fence help` | 帮助 |

要点：

- **通用规则对每个对话生效**（包括新开的对话）；**会话规则只作用于当前会话**。两层都为空时渲染空字符串 → 零注入、零 token。
- 规则改动**下一轮立即生效**，不需要重启。
- 单条 ≤ **2000** 字符；每层最多 40 条 / 渲染总 2400 字符封顶。
- 规则里**不要写 `{{ }}`**：宿主的 `interpolate()` 遇到未注册变量会抛错。插件已用 `try/catch` 兜底（降级为空），但内容会静默失效。

### 1.3 直接编辑围栏文件（0.7.0 起，单个 JSON）

围栏文件默认 `<DSH_HOME>/dialog-fence/fence.json`（`/fence dir` 会打印实际路径）。
本机 `DSH_HOME` = `C:\Users\<你>\AppData\Roaming\dsh-desktop\harness`。

> 0.5.0 起这个路径**不再跟着插件包目录走**：宿主半边的 `resolveDshHome()` 从插件所在目录向上找
> 第一个同时含 `profiles/` 与 `sessions/` 的祖先（= DSH home）。这样无论插件是
> `<home>/dialog-fence/`（开发态 `file:///`）还是 `<home>/profiles/.generations/live/<gen>/node_modules/dsh-dialog-fence/`
> （组合包快照），数据都落在同一个 `<home>/dialog-fence/`，升级换代不丢。
>
> 0.7.0 起二级路径是 `fence.json`（不再有 `rules/` 目录）。老的多 txt 目录会在首次启动时被**读取并迁移**，
> 老文件原样保留（可手工删除）。迁移只在「围栏文件不存在」或「围栏文件存在但内容为空」时发生，
> 已有数据的围栏文件**绝不会被覆盖**。

```json
{
  "version": 3,
  "enabled": true,
  "rules": [
    "通用规则 1：对每个对话都生效",
    "通用规则 2：……"
  ],
  "ruleEnabled": [true, false],
  "mutedSessions": ["session-<uuid>"],
  "sessions": {
    "session-<uuid>": {
      "enabled": true,
      "rules": ["只对这个会话生效的规则"],
      "ruleEnabled": [true]
    }
  }
}
```

`ruleEnabled` 是 0.13.0 新增的**可选**并行数组，与 `rules` 同下标一一对应：`false` = 那一条暂时不注入。
不写、写短了、整段删掉都等于「全部启用」，所以老文件拿来就能用，不需要迁移。

`mutedSessions` 是 0.14.0 新增的**可选**名单：列进去的会话**通用与专属都不注入**（等于这条对话没有围栏），
但它自己的 `sessions.<id>.rules` 一条都不删，从名单里去掉即原样恢复。不写 / 空数组 = 所有对话都使用围栏。
名单落盘前会消毒（只留 `[A-Za-z0-9._-]`）、去重、`sort()`，所以同一组多选无论勾选顺序如何，文件字节都一样。

注入顺序：先 `rules[]` 的 1..N（跳过 `ruleEnabled[i] === false` 的），再把该会话启用的专属规则接在后面连续编号 —— 停用的条目不占序号，所以编号永远从 1 连续。

行为规则：

| 你做的事 | 结果 |
|---|---|
| 在 `rules[]` 里加一条 | 对**所有对话**立即生效（包括新开的），默认启用 |
| 在 `sessions.<id>.rules[]` 里加一条 | 该会话**自动启用**并生效（即使没写 `enabled`） |
| 改一条正文 | 下一轮注入的文本跟着变 |
| 删掉一条 | 该条规则消失，后面的序号自动前移；`ruleEnabled` 对应位同步删除，不会错位 |
| `ruleEnabled[i] = false` | 那一条保留正文但不注入、不占序号（0.13.0 起） |
| `mutedSessions` 里出现某会话 id | 这条对话**整段零注入**（通用 + 专属都不注入），规则一条不删；移出名单立刻恢复（0.14.0 起） |
| 空字符串 / 全空白 | 不算规则，跳过 |
| `sessions.<id>.enabled: false` | 保留正文但不注入该会话层 |
| 顶层 `enabled: false` | 两层一起静音，文件原封不动 |
| JSON 语法错误 | **不抛错、不改写文件**，本轮降级为零注入并在日志里 warn；修好即恢复 |

⚠ **写这个文件请用 UTF-8（无 BOM）**。历史事故见「变更记录 · 事故 1」。插件已做编码自动探测（UTF-8 BOM / UTF-16LE 都能读），但仍建议用编辑器或 `node` 写，不要用 PowerShell 的 `Set-Content` / `Out-File` / `>` 重定向。

### 1.4 打开文件夹 / 自定义位置（0.7.0）

- 设置页顶部有 **「打开文件夹」**：Windows 用 `explorer.exe /select,<围栏文件>`（文件还不存在时打开其所在目录），macOS 用 `open -R`，Linux 用 `xdg-open`。子进程 `detached + stdio:'ignore' + unref()`，**不会卡住宿主**。
- **0.8.0 起**：点了之后按钮下方一定会出现一行结果（`已打开围栏文件夹` / `没有打开窗口` / `上一次启动资源管理器失败：…`）。0.7.0 及以前这行不存在，导致成功与失败在界面上完全一样（用户 CR-15 报的「点了没反应」）。
- 旁边 **「更改位置」** 展开一行绝对路径输入框 + 「迁移」：
  - 必须是**绝对路径**，且以 `.json` 结尾（只给目录会自动补 `fence.json`）；
  - 迁移把当前数据写到新位置，再把 `<BASE_DIR>/location.json` 写成 `{"file":"<新路径>"}` 指针；
  - **原文件不删**（避免误操作丢数据），需要时自己清理；
  - 想回默认位置：删掉 `location.json`（或把它改成指向默认路径）即可。
- 优先级（高的先赢）：环境变量 `DIALOG_FENCE_FILE` → `<BASE_DIR>/location.json` → `<BASE_DIR>/fence.json`。
- 等价命令：`/fence dir`、`/fence open`、`/fence file D:\我的围栏\fence.json`。

## 二、怎么改插件代码 / Changing the plugin

1. 编辑 `harness/dialog-fence/index.js`（宿主半边）或 `harness/dialog-fence/client.js`（浏览器半边）。
2. **必须重启 DSH Desktop 才生效**（实测：`dsh-hmr` 未重载本插件，见「变更记录 · 事故 2」）。`client.js` 同样需要重启 —— 浏览器 bundle 由 `dsh-client-modules` 在启动时按 graph 组装。
3. 改完先跑四个无宿主测试（不需要宿主，也**不碰线上 `fence.json`**）：

```powershell
$env:ELECTRON_RUN_AS_NODE="1"
$exe = "D:\DSH Desktop\DSH Desktop.exe"
$dir = "C:\Users\<你>\AppData\Roaming\dsh-desktop\harness\dialog-fence"
& $exe "$dir\test\smoke.mjs"
& $exe "$dir\test\route.mjs"
& $exe "$dir\test\client.mjs"
& $exe "$dir\test\render.mjs"
```

> 注意：`& $exe` 之后 `$LASTEXITCODE` 在 Electron 下是空的，**判定要用输出里有没有 `OK all`**；
> 要拿真实退出码请用 `Start-Process -Wait -PassThru`。

期望输出四行：

```
OK all dialog-fence smoke assertions passed
OK all dialog-fence route assertions passed
OK all dialog-fence client bundle assertions passed
OK all dialog-fence render assertions passed
```

四个测试各管一段：

| 测试 | 覆盖 |
|---|---|
| `smoke` | 宿主逻辑：隔离性、命令路径、上限、编码兼容、`ctx.inject(['connection'])`、**所有规则落在一个 `fence.json`**、**直接手改 JSON 四种情形**、**多 txt 自动迁移（含空文件迁移 / 有数据不覆盖）**、**坏 JSON 只降级**、**`/fence file` 改位置 + `location.json`**、**`openFolder` 在 `DIALOG_FENCE_NO_OPEN=1` 下不弹窗**、**多行规则往返与 `\r\n` 归一（0.9.0）** |
| `route` | HTTP API：GET（overview / snapshot / `?scope=common`）、HEAD、POST、按**下标**寻址的 update/remove、`toggleGlobal` / `switch` / `setFile` / `openFolder`、非法入参 400、405 |
| `client` | 浏览器 bundle 形态：`__ModuleLoader__.load`、`factory`、导出、无裸 `import`、五个 slot 注册签名、**4 个 `createElement('textarea')`（规则编辑态 + 三处新建框）、唯一保留的 `<input>` 是围栏文件路径框、`Enter` 归还换行、提交走 `Ctrl/Cmd+Enter`**、**设置页不出现 sessionId**、`dsh.client` 解析链复算 |
| `render` | 用 DSH 自带的**真 React 18** 把头部按钮、浮层、设置页真渲染一遍（`react-dom/server` 的 `renderToStaticMarkup`），确认组件在真 hooks 运行时下不违规、首帧产出预期 DOM |

`render` 只看首帧 —— `renderToStaticMarkup` 不执行 `useEffect`，「点开面板拉数据」仍需浏览器验证（见下方「验证面板是否真的挂上了」）。找不到真 React 时会打印 `SKIP dialog-fence render test` 并 exit 0。

测试通过 `DIALOG_FENCE_HOME`（以及 `DIALOG_FENCE_FILE`）把插件指向系统临时目录里的一次性沙箱，跑完自动删除，并在结尾断言线上文件一字未动。

### 临时停用 / 卸载

**只关注入（不卸载插件）**：本包详情页配置区里的总开关，或直接改 `fence.json` 的顶层 `enabled`，或 `/fence switch off`。

**方式一（推荐，0.5.0 主推形态）：插件页官方卸载**

左侧「插件」→「已安装」→ 点 **dsh-dialog-fence** → 详情页里点「卸载」。
它走 `pluginManager.removeBundle` → Desktop 的 `profileBundlePackageBackend.remove`，
会把 profile `dependencies` / `dsh.profile.bundles` / `pnpm.overrides` 一并清掉。
围栏文件（`<DSH_HOME>/dialog-fence/fence.json`）**不会**被删，重新装回来即恢复。

**方式二：loader 开关（不卸载，只停进程）**

本包详情页的行列表里每个 loader 行都有启用/禁用开关（`pluginManager.setPluginEnabled`）。
注意这与围栏的业务总开关是两件事：loader 开关会**停掉整个插件**（按钮、命令、路由全消失），业务总开关只停注入。

**方式三（仅 `file:///` 开发形态）：用安装器卸载**

```powershell

node scripts/install.mjs status         # 查当前状态（会统计会话数与规则数）
```

**方式四（仅 `file:///` 开发形态）：手工编辑补丁层**

在 `harness/profiles/web/cordis.patch.yml` 里找 `- id: dialog-fence` 那个 insert 块：

```yaml
- insert:
    - id: dialog-fence
      name: "file:///C:/Users/%3C你%3E/AppData/Roaming/dsh-desktop/harness/dialog-fence/index.js"
```

- 临时停用：在 `name:` 同级加 `disabled: true`。
- 彻底卸载：删掉整个 `- insert:` 块（含上方注释）。围栏文件可保留，重新挂回即恢复。

> ⚠️ **组合包形态与 `file:///` 形态互斥**。两者同时存在时会有两条 loader 行，
> 槽位被重复注册。从 `file:///` 切到组合包之前先 `scripts/install.mjs uninstall`。

### 验证面板是否真的挂上了

1. **设置左栏 → 「对话围栏」**：应能看到总开关、**围栏文件路径**、`[打开文件夹]`/`[更改位置]` 和**通用规则列表**（0.6.0 起这里是主入口）。
   看不到菜单项 → `settings.section` 注册未生效（客户端没重启或 bundle 没更新）。
2. 通用规则列表是否有内容。没有 → 走 `GET api/dialog-fence?scope=common` 看看返回什么，或直接看 `fence.json` 的 `rules[]`。
3. 会话右上角是否出现「围栏」按钮，**点开后应看到与设置页同一套四张卡片**（0.12.0 起；0.7.0 之前只显示会话层，是 CR-14 第 1 条报的缺陷）。
   按钮都没出现 → 客户端 bundle 未被扫到，检查 `package.json` 的 `dsh.client` 与 `exports['./client']`。
   卡片出来了但**浮层里没有对话下拉** → 大概率还在跑旧 generation（改 `client.js` 后必须重装 + 重启）。
4. 左侧「插件」→「已安装」里是否有 **dsh-dialog-fence** 卡片，点进去详情页里是否有围栏配置区。
   没有卡片 → 组合包没装成（查 `plugin_manager list_bundles` 是否有该条目）；
   有卡片但没配置区 → `plugins.bundle.config` 的 `key` 不是 `dsh-dialog-fence`，或注册未生效。

   - 返回 **404** → 宿主路由没注册。0.2.x 曾因 `ctx.get('connection')` 拿到 `undefined` 而必然 404，0.3.0 已改为 `ctx.inject(['connection'], cb)`（见设计文档 5.2）。
   - 返回 **400** → 请求体形状不对（通用层必须带 `"scope":"common"`）。

## 三、排查手册 / Troubleshooting

### 症状：围栏文本没出现在下一轮

按顺序查：

1. **总开关是否被关掉** —— `/fence status` 第一行会显示全局状态；或看 `fence.json` 的顶层 `enabled`。
2. **通用层有没有规则** —— `fence.json` 的 `rules[]` 是否非空（设置页里应能看到它们）。
3. **（查会话层时）会话 id 对不对** —— `/fence` 会打印当前 `sessionId`，与 `fence.json` 里 `sessions` 的键逐字比对。
4. **该层是否有非空规则** —— 数组里没有条目、或全是空白字符串，就等于没有规则。
5. **该会话是否被显式停用** —— `sessions.<id>.enabled` 为 `false` 时保留正文但不注入。
6. **文件编码与 JSON 语法** —— 用这条命令看首字节（把路径换成实际文件）：

   ```powershell
   $p="C:\Users\<你>\AppData\Roaming\dsh-desktop\harness\dialog-fence\fence.json"
   $b=[System.IO.File]::ReadAllBytes($p); "$($b.Length) bytes, first: $($b[0]),$($b[1]),$($b[2])"
   ```

   - `123,10,32` 或 `123,34,118` = `{` 开头 → UTF-8 正常 ✔
   - `255,254,123,0` = UTF-16LE（能读，但建议改回 UTF-8）
   - `239,187,191` = UTF-8 BOM（能读，但建议去掉）
   - 语法错的话插件会在控制台打 `[dialog-fence] 围栏文件解析失败，本轮按空围栏处理（文件未被改写）: …`，**文件不会被改坏**。
7. **插件是否被加载** —— 重启后 startup 日志里搜 `dialog-fence`；插件本身只 `console.log` 一行 `ready: file=<路径> context=dialog-fence:rules@118`，不写 DSH 日志文件。
8. **迁移是否发生** —— 若刚从 0.6.x 升级，日志里应有 `[dialog-fence] 已从多 txt 目录迁移到单文件: …`。没有且 `fence.json` 的 `rules[]` 是空的，说明老目录里也没东西，或围栏文件已被别的数据占着（不会覆盖已有数据）。

> 两层模型意味着：**设置页里配的规则对所有对话生效**，会话专属那一层只影响当前对话。
> 当某个对话「明明配了却看不到」时，先分清那条规则是在 `rules[]` 里还是在 `sessions.<某个 id>.rules[]` 里。
> 而「设置页配了、会话头部浮层里却看不到」是 0.7.0 已修的渲染缺陷（面板原来只读会话层）。

### 症状：改完 index.js / client.js 没生效

分两种形态：

- **`file:///` 开发形态**：正常现象，**重启 DSH Desktop** 即可（`dsh-hmr` 不重载本插件）。
- **组合包形态**：除了重启，还要**重装**。官方安装器把源码复制进
  `profiles/.generations/live/<gen>/node_modules/dsh-dialog-fence/`，改源码目录不会影响那份副本。
  插件页「已安装」→ 本包 → 卸载 → 再「添加插件」装一次。
  判断装的是哪份：`plugin_manager list_bundles` 里有 `dsh-dialog-fence` 条目 = 组合包形态；
  没有 = `file:///` 形态。

### 症状：面板左下角显示 `HTTP 404`

0.3.0 已修复（根因见设计文档 5.2：`ctx.get('connection')` 在 `apply()` 时刻取到 `undefined`，路由被静默跳过）。
若仍出现：

1. 确认已完整重启 DSH（不是只刷新页面）。
2. 搜日志里有没有 `[dialog-fence] route ready` 这一行 —— 有则路由已注册，404 应是路径写错；没有则 `connection` 服务没就绪或插件被禁用。
3. 确认访问的是 `api/dialog-fence`（document-relative），不是 `/api/dialog-fence`（浏览器里带前导斜杠也行，但别写成绝对 URL）。

### 症状：`git push` 被拒，`refusing to allow an OAuth App to create or update workflow`

完整报错（实测原文）：

```
! [remote rejected] master -> master (refusing to allow an OAuth App to create or update workflow
`.github/workflows/test.yml` without `workflow` scope)
```

原因：推送用的凭据**没有 `workflow` scope**。GitHub 对 `.github/workflows/*` 的新增与修改要求一条独立权限，`repo` 权限不覆盖它。

判定（只看 scope 列表，不回显令牌内容）：

```powershell
$cred = "protocol=https`nhost=github.com`n`n" | git credential fill
$tok = ($cred -split "`n" | Where-Object { $_ -like 'password=*' }) -replace '^password=',''
curl.exe -s -I -H "Authorization: Bearer $tok" https://api.github.com/user |
  Select-String 'x-oauth-scopes'
```

- 输出 `X-OAuth-Scopes: gist, read:org, repo` → 缺 `workflow`，按下文补。
- 输出里已有 `workflow` → 不是这个原因（确认推的是同一个账号、同一个远端）。

修复（device flow，令牌不经过命令行、不落盘）：

```powershell
$env:HTTPS_PROXY='http://127.0.0.1:7897'    # 本机直连 github.com 会超时，必须走代理
gh auth refresh -h github.com -s workflow
```

按提示在浏览器打开 <https://github.com/login/device>、输入一次性码、批准授权。
**本机实测（2026-10-21）**：`gh auth refresh` 完成后再用上面的 `git credential fill` 取凭据，`x-oauth-scopes` 已变成 `gist, read:org, repo, workflow`，无需再动 Git Credential Manager；随后 `git push` 一次通过。

两个坑：

- **不设代理会失败**，报 `Post "https://github.com/login/device/code": ... wsarecv: 由于连接方在一段时间后没有正确答复...`。`http.proxy` 是 git 自己的配置，`gh` 不读它，要单独给 `HTTPS_PROXY`。
- `gh auth refresh` 在 DSH 里用后台任务跑时，stdout 被缓冲看不到设备码 —— 用 `Start-Process ... -RedirectStandardOutput` 写文件再读。

替代方案（不改 token 权限）：把 `.github/workflows/*.yml` 从这次提交里摘出去，先推其余改动，再到 GitHub 网页新建文件 —— 网页端走浏览器会话，不受 token scope 限制。价格是 CI 就绪晚一步，而分支保护的「Require status checks」必须等 workflow 成功跑过一次才选得到。

### 症状：force push 之后旧内容还能被匿名访问（发布事故）

**这不是 bug，是 GitHub 的行为**：`git push --force` 只移动 ref，旧 commit 对象留在服务端且**匿名可取**——只要知道 SHA 或旧 tag 名。

判定（不带头、不带任何凭据）：

```powershell
# 旧 SHA 能否直接取到文件
curl.exe -s -o NUL -w '%{http_code}\n' `
  "https://raw.githubusercontent.com/<owner>/<repo>/<旧SHA>/docs/运维手册与变更记录.md"
# 旧 tag 能否打包下载
curl.exe -s -o NUL -w '%{http_code}\n' `
  "https://codeload.github.com/<owner>/<repo>/tar.gz/<旧tag>"
```

返回 `200` = 还在；`404` = 真的没了。**这两个 200/404 才是「清除了没有」的判据**，而不是「新 clone 的历史里 grep 不到」。

处置顺序：

1. **先止血**：`gh api --method PATCH repos/<owner>/<repo> -F private=true`，再匿名取仓库页确认 `404`。
2. 判断要不要更彻底：只要旧对象里含个人信息，而仓库曾经 public 过，就应视为已暴露。
3. GitHub **没有自助删除不可达对象**的入口（也无法靠 force push 触发回收）。可行的两条路：①**删库重建**（最彻底，旧对象随旧仓库消失）；②保持 private，联系 GitHub Support 请求回收。
4. 选①时，删之前先把 description / topics / has_discussions / actions 权限 / 默认分支全部读出来（见「四、变更记录 · v0.9.1 ⑧」的重建清单），否则重建后要一个个猜。
5. 重建后**必须**复验：匿名 clone 成功、worktree 与全历史 0 命中、**旧 SHA 变 404**、CI 绿、分支保护重新挂上 `test`。

> 一般化的教训：验证「已经删掉」时，要去取那个本该消失的东西；只验证「剩下的东西是干净的」会把这类事故放过去。

### 症状：缓存命中率突然掉

用 `acp_cache` / `/acp-cache` 看归因。判定口诀：

- `divergence ... tail-append` 或 `tail(params/notes)` → 正常，前缀没坏（围栏改动属于这一类）。
- `mid-history` + `no fold/switch/restart attribution` → 先看 `bili.log` 里 `strict-echo: injected blank reasoning_content on N assistant tool-call message(s)`。这是 **billion-context 自己**在改写历史 assistant 消息，与围栏无关（见「变更记录 · 实测 3」）。
- `PROVIDER-SIDE MISS` / `UPSTREAM TTL EXPIRY` → 上游缓存过期或被驱逐，与本插件无关。

### 真要让围栏永不被压缩

编辑 `C:\Users\<你>\.config\billion-context\billion-context.json`：

```json
{ "compress": { "protectedTools": ["durable/*"] } }
```

代价：旧快照永不折叠，上下文单调增长。默认**不建议**。

## 四、变更记录 / Change log

### 2026-10-30 · v0.14.0 整条对话不使用围栏（多选）

**起因（用户原话）**：「围栏再增加功能，可以选择对哪些会话不再使用围栏规则，对话可以多选，但是要注意UI，不要多选了以后把别的东西挤出去」。要的是「这类对话暂时别管我」，不是「把这些对话的规则删掉」。

**改法**：

- 存储层加顶层**可选名单** `mutedSessions: string[]`（缺省 = 全都使用，老文件零迁移，版本号仍是 `3`）。
  没往 `sessions[id]` 里加 `muted` 字段：那会顺带创建一条会话记录，让「豁免」在 `knownSessions()` / `overviewOf().sessions` / 面板「N 个对话设置过专属规则」里凭空多出一行。
- 注入层 `fenceTextFor()` 在总开关判定之后、拼通用规则之前一行 `if (isSessionMuted(fence, sessionId)) return '';`。
  位置不能挪进 `isSessionEnabled()` —— 那个函数的语义是「专属层要不要生效」，通用层照样会漏进来。
- 落盘前统一 `normalizeMutedSessions()`：`sanitizeSessionId()` 消毒 → 跳空 → `Set` 去重 → `sort()`。
  排序是为了**字节稳定**：同一组多选无论勾选顺序如何都写出同一份文件，否则每点一次勾都会触发一次 runtime-context 重新投影（白花 token）。
- HTTP 新增 `{ action: 'mute', sessions: [...], muted: bool }`，一次可传多个；它**与单个 sessionId 无关**，
  所以进了 `handleApi()` 的全局白名单，且 `applyAction()` 里必须放在 `sessionId === ''` 那条 400 校验之前。
- 命令层 `/fence mute` / `/fence unmute` / `/fence muted`（带会话 id 则操作指定会话）；`/fence status` 多一行「本会话豁免」。
- 快照：`snapshotOf` 增 `muted`，`overviewOf` 增 `mutedSessions`，`knownSessions` 每行增 `muted`。

**先红后绿（实测读数）**：

- 红：改 `index.js` 之前跑新增的 `test/sessionmute.mjs` → `FAIL: 22 处不满足`，典型几行是
  `豁免请求 200 — {"ok":false,"error":"缺少或非法的 sessionId"}`、
  `豁免后不注入通用规则 — Dialog fence (...):\n1. 通用规则甲\n2. 甲专属规则`、
  `清单行带 muted 标记 — {"sessionId":"session-legacy","enabled":true,"ruleCount":1,"activeRuleCount":1,"chars":5}`。
- 绿：改完 `node test/sessionmute.mjs` → `OK all dialog-fence session-mute assertions passed`；
  `ELECTRON_RUN_AS_NODE=1 DSH_INSTALL='J:\DSH Desktop' npm test` 九套全绿（这次连 render 也真跑了，
  不是 SKIP；`theme tokens: 403 declared, 13 used by client.js`）。

**这次踩的坑（UI 那条，用户点名的）**：不能把豁免行塞进「某个对话的额外规则」那两行
`dialog-fence-picker-row`。`test/render.mjs` 3.7 段把它们钉成**恰好 2 个**，塞进去勾一个对话就多一行匹配，
断言立刻红 —— 而这正是用户担心的「多选了以后把别的东西挤出去」。最终自成一套行，
并且宽度约束做成单向：**只有**对话名 `.dialog-fence-mute-name` 带 `flex:1;min-width:0` + 单行省略号，
勾选框 / 状态标记 / 底部两个按钮全部 `flex:none;white-space:nowrap`。于是勾选数量只影响这一列的
高度（`max-height:180px` 后自己滚动），横向一个像素都不动。`test/client.mjs` 5.45 段
（8 条源码级断言）与 `test/render.mjs` 3.8 段（DOM 级 + 「picker-row 仍是 2 个」）把这条钉成回归。

**第二个坑（PowerShell 改中文源文件）**：用 `Get-Content -Raw` + `-replace` + `WriteAllText` 批改含中文的
`.js` / `.mjs`，会把 UTF-8 当 GBK 读进来 → 整文件乱码，`node --check` 报
`SyntaxError: Invalid or unexpected token`，中文变 `閫氱敤瑙勫垯鐢`。**中文文件只能用 write/edit 整段改写**。
本次 `test/sessionmute.mjs` 因此被写成乱码一次，整体重写过。

**第三个坑（红灯信息被吞）**：测试里直接写 `body.mutedSessions.includes(...)`，在旧实现下会抛
`TypeError: Cannot read properties of undefined (reading 'includes')` 直接中断，后面几十条断言看不到。
统一过 `const listOf = (body) => Array.isArray(body?.mutedSessions) ? body.mutedSessions : [];`。

### 2026-10-28 · v0.13.0 每条规则一个启停滑块

**起因（用户原话）**：「围栏的每一条配置加一个单独控制是否启用的滑块按钮，用来随时控制某一条围栏暂时启用或者不启用，默认是配置以后就启用」。此前只有两个粒度：总开关、每会话开关。想临时让某一条闭嘴，唯一办法是删掉再重写。

**改法**：

### 2026-10-27 · v0.12.4 专属规则下拉不再混进工作区名；四个入口钉成同一个组件

**起因（用户原话）**：「围栏的专属设置里出现了很多工作区的名字选项，排查一下原因，并且保证多个入口进来的设置界面UI同步」。配图是设置页「某个对话的额外规则（可选）」卡片的 `对话` 下拉展开，里面 `harness` / `workspace` 各重复多次，夹在真实对话标题之间。

**根因（实测，不是猜的）**：那些选项不是「工作区被当成了对话」，而是「建了但一句话都没说过」的空对话。链路是这样：

1. 空对话在宿主 `sessions` store 里带 `blank: true`，没有 `title`；
2. `dsh-api-session-controller` 的 `displayTitleOf(title, cwd, id)`（`lib/types/client/sessions/service.js`）在没有 title 时退回 `workspaceTitleOf(cwd)`，也就是 **cwd 的 basename**；
3. 工作区根目录恰好叫 `harness`（`C:\...\dsh-desktop\harness`）与 `workspace`（`D:\workspace`），空对话又多，于是下拉里就成了一串重复的 `harness` / `workspace`；
4. `client.js` 的候选循环当时只挡了 `origin === 'subagent'`，**没挡 `blank`**——官方侧边栏是整行藏掉的（`dsh-client-ui-workspace` 里 `node.blank ? t("session.new") : ...`），我们漏了这一步。

磁盘侧也对得上：`harness\sessions\` 下 99 个会话目录里有多个 `files=0` 的空目录。

**改法（最小）**：候选循环加一行 `if (row?.blank === true) continue;`。只挡 `blank`，不挡「没起名字但真的用过」的对话——后者仍列出，显示成 `未命名对话 N`。

- `registrations[2].component === registrations[3].component === registrations[4].component`；
- 浮层源码里出现 `FencePage`（不是它自己的一份实现）；
- 同一个 props 在两个入口渲染出的 HTML 逐字节相同（`assert.equal(sameA, sameB)`）；

### 2026-10-20 · v0.7.0 单文件 JSON + 打开文件夹 / 自定义位置 + 面板同步

**起因（用户 CR-14 原话，三条）**：

> 「1.右上角的围栏按钮点开以后没有同步出现配置，需要修复

**① 缺陷 1 的根因（不是缓存，是渲染分支）**

`Panel()` 只渲染 `entryOf(sessionId).rules` = **会话层**；用户实际在配的是**通用层**

`HeaderAction` 的 `refresh` 也一直是成功的 —— 数据早就到了浏览器，只是组件没用它。
徽标同理：`count = entry?.rules?.length` 只数会话层，所以显示「1」而不是「11」。

修法（最小改动）：`Panel()` 改成两段渲染 ——「围栏规则（对每个对话生效）」可编辑 +
「本会话专属规则」可编辑可增删；徽标与 meta 的字符/token 数都改成两层合计。

**② 需求 2：打开文件夹 + 自定义位置**

  `{ok:true, opened:false, reason:'test-mode'}`（测试用）。
- 新动作 `setFile` → `moveFenceFile(target)`：必须绝对路径 + 以 `.json` 结尾（给目录就补 `fence.json`）；
  把当前数据写到新位置，再写 `<BASE_DIR>/location.json` = `{"file":"<新路径>"}`。
  **原文件不删**；删掉 `location.json` 即回默认位置。
- 优先级：`DIALOG_FENCE_FILE` 环境变量 > `location.json` > `<BASE_DIR>/fence.json`。
- 命令侧同步：`/fence dir`、`/fence open`、`/fence file <绝对路径>`。

**规则本身也踩过坑：只匹配「名 + 姓」会放过裸名。** 第一版写成「名 + 可选分隔 + 姓」，于是文档里一句「只查了本机名（裸名形态）与 hostname」被放过——而那句话恰好把本机名写了出来。发现它的方式不是再读一遍文档，而是**重建后用全新 clone 复核**：按本机名做大小写不敏感检索命中 1 处，扫描器却是绿的。改法是把规则放宽到只匹配名（`\b<名>\b`），并补一条单独匹配 `姓-IT` 的规则。

改完必须做**反向验证**，否则「规则太松」和「真的没有泄漏」读数完全相同：临时造一个含裸名的文件 → 期望扫描器变红 → 删掉文件 → 期望转绿。实测两侧读数都留下了（红：`[real-name] <探针文件>:1  <本机名>`；绿：`0 处命中`）。

这条教训与文档里的编号问题同源：**「我搜过了没有」的强度等于检索模式的强度**，所以收尾不能靠再人工搜一遍，只能靠把泄漏面变成会自己报错的测试。

**但第一版扫描器漏了一大块：它只读文件，不读 commit message。**

公开仓库里最容易被人读到的东西恰恰是 `git log`。第一版转 public 之后才复核到，三条 commit message 里留着内部对话编号和一条逐字的用户原话引用（一条是「按用户反馈（编号）三条改」，一条把用户原话原封不动写进正文）。RED 读数（编号按扫描器规则替换成占位写法）：

```
FAIL: 扫描 22 个待公开文本文件 + 13 条 commit message，命中 3 处
  commit 8ae6fb57:0  <内部编号> × 2
  commit 27bd6fff:0  <内部编号> × 1
```

修法是给扫描器加 `scanCommitMessages()`：`git log --branches --tags --format=%H` 取所有可达 commit，逐条 `git log -1 --format=%B`，复用同一套 5 条规则。两个必须注意的点：

- **用 `--branches --tags` 而不是 `--all`**。`--all` 会把 `refs/original/*`（filter-branch 留下的旧历史备份）算进来，于是扫到的全是「已经不该存在」的旧提交，改不动也删不掉，只会让测试永久红。
- 不是 git 仓库时（比如从 tar.gz 解压出来的源码）要静默跳过，只跑文件扫描，否则 `execFileSync('git')` 直接抛错。

汇总行随之变成「扫描 N 个待公开文本文件 + M 条 commit message」，否则「文件数没变但其实是绿的」这种假象会再发生一次。

**② 重写 git 历史（10 个 commit、9 个 tag）**

- 目的：清掉历史 blob 里的本机用户名。全部 **53 处，且全部是绝对用户路径**，没有一处是作者名——author/committer 早已是 `ILoveHAKU <ILoveHAKU@users.noreply.github.com>`，无需改。
- 手段：`git filter-branch --tree-filter` + perl 一个 pass 同时替换三类 token，`--tag-name-filter cat -- --all` 一并重建 tag。
- 结果：路径里的用户名 → 占位符 `C:\Users\<你>`（URL 形态 `%3C你%3E`）；`mNNNNN` → `CR-01`…`CR-16`（按首次出现的时间顺序，保持唯一且可交叉引用）；真实 session id → `session-<uuid>`。
- **为什么编号不能删空**：它们在正文里是唯一的引用锚点（「已被 X 推翻」「见 5.5.7」），删掉会让交叉引用失去指代对象。
- **踩坑**：`refs/original/` 只是备份引用，`git log` 默认看不见它，但 `git push --all` / `--mirror` 会推——推送前必须确认。
- 回滚：本机 `%TEMP%\dialog-fence-oss-backup-*\repo-full.bundle`（`git bundle create --all` 的产物），`git clone '<bundle>' '<target>'` 即可还原重写前的完整仓库。

**②-b commit message 还得再重写一遍（第一遍只改了 tree）**

上面那次 `--tree-filter` 只碰工作树，commit message 一个字没动。而我当时判断「message 里 0 命中」用的是一条**范围错误的检索**：只查了本机用户名与 hostname，没查内部编号（`mNNNNN`）。第二轮是用扫描器（已加上 message 扫描）扫出来的，命中 3 条。

修法：`git filter-branch -f --msg-filter` + 一个 node 脚本。脚本按**首行 subject 精确匹配**整条替换，而不是正则微调——因为要删的原话跨好几行，用正则抠句子会把语法抠坏。三条 message 的改写原则是「只留问题与做法，不留对话记录」：

| 原写法 | 改成 |
|---|---|
| `User report (编号): 点击打开文件夹没有反应` | `Problem: clicking "open folder" appeared to do nothing.` |
| 中文原话逐字引用 + `This reverses a constraint set in 0.3.0 (编号 asked for no textarea)` | `Problem: the single-line inputs hurt readability…` / `an earlier decision in 0.3.0 (no textarea)` |
| `the external review checklist had found only 4` | `a manual pass had found only 4` |

**判断标准不是「删掉所有中文」**：像 `设置左栏一级菜单` 这种是产品功能名，属于必要的技术描述，保留。要删的是「谁在什么对话里说了什么」。

**踩坑：Electron 当 node 用时，stdin 管道和重定向都不可靠。** 用 PowerShell 管道喂 stdin → `Error: EPIPE: broken pipe, write`，输出空；用 `cmd /c "... > out.txt"` → PowerShell 的 `>` 写成 **UTF-16**，读回来每个字符间夹着 NUL，替换静默不生效。稳的做法是先用 node 以 `utf8` 把输入落盘，再 `cmd /c "<exe> <script> < in.txt > out.txt"`，读回用 `[System.Text.Encoding]::UTF8.GetString([System.IO.File]::ReadAllBytes(...))` 显式解码。改完必须验证「旧词已消失、字节数合理」，不能只看 exit code。

**⑥ 推送（踩坑：`workflow` scope）**

第一次 `git push --force-with-lease --tags` 被 GitHub 拒绝：

```
! [remote rejected] master -> master (refusing to allow an OAuth App to create or update workflow
`.github/workflows/test.yml` without `workflow` scope)
```

本机凭据是 OAuth App token，原 scopes 只有 `gist, read:org, repo`。`gh auth refresh -h github.com -s workflow` 走 device flow 补权限后，凭据变成 `gist, read:org, repo, workflow`，同一条 push 通过。细节与判定命令见「三、排查手册 · 症状：`git push` 被拒」——**这个坑在任何新机器上都会重演**，因为只要本次改动含 `.github/workflows/`，`repo` scope 就不够。

另有两个容易误判的现象：

- `git push` 成功后 PowerShell 仍显示 `[exit code: 1]` —— git 把 `To https://…` 这类进度写 stderr，pwsh 会当 `NativeCommandError`。**判据取 `git ls-remote` 的实际 ref 值，不看退出码。**
- 本机 `ssh -T git@github.com` 是 `Permission denied (publickey)`（`~/.ssh/id_rsa` 存在但未在 GitHub 上注册对应公钥）。远端走的是 HTTPS + Credential Manager，**不要**因为 SSH 失败就以为没有推送能力。

**⑦ 转 public 与分支保护**

- 仓库先保持 private 完成全部推送，**最后一步才转 public**。原因：转 public 会禁用 private 仓库上的 push rulesets（GitHub 的限制），先公开后配保护是正确顺序。
- **分支保护只能对 public 仓库或付费账户开启**。private 状态调 API 会返回 `403 Upgrade to GitHub Pro or make this repository public to enable this feature.` —— 这是私有仓库的正常限制，不是权限问题。
- 转 public 后立刻配 master 保护（实测生效）：

  | 项 | 值 |
  |---|---|
  | Require status checks | `test`（`strict: true`，即要求分支最新） |
  | 禁止强推 | `allow_force_pushes: false` |
  | 禁止删分支 | `allow_deletions: false` |
  | 要求对话解决 | `required_conversation_resolution: true` |
  | `enforce_admins` | `false`（保留自己紧急推送的余地） |

  这里的 `test` 就是 `.github/workflows/test.yml` 里 `jobs.test.name: test`。**这正是不加那个 workflow 会自锁的原因**：`Require status checks` 只能选到曾经成功跑过的 job 名，没有 workflow 时列表是空的，配了就是一个永远 pending 的保护。

- 转 public 后做**匿名**复验（不带任何凭据，模拟陌生访客）：

  ```
  repo 页面 HTTP 200 / raw README HTTP 200
  api.github.com/...  "private": false, "visibility": "public"
  git -c credential.helper= clone ... → commits=12, files=25, tags=9
  匿名克隆的 worktree + 全部历史 → 0 命中
  ```

  最后一条是关键：`credential.helper=` 清空后仍能 clone，才证明「陌生人真的能拿到」，而不是本机凭据在背后兜底。

- CI 在转 public 前后各跑过一次，均 `success`（约 11 秒）。日志里 `test/render.mjs` 如预期打印 `SKIP dialog-fence render test: real React not found next to this DSH install`，其余四套 `OK all …`。

**已知限制**：`test/render.mjs` 在 CI 上恒定 SKIP，所以「真 React 首帧渲染」这一层在 CI 里没有覆盖，只能本地验证。

**⑧ 严重失误与最终处置：force push 不会删掉旧 commit 对象**

这一节是本轮最该记住的事，因为它推翻了一个很自然但不成立的假设。

- **假设（错）**：「本地历史重写干净 + force push 覆盖远端 = 远端干净」。
- **实际**：force push 只移动 ref，**旧 commit 对象仍然留在 GitHub 上，而且匿名可取**。实测（不带任何凭据）：

  ```
  GET https://raw.githubusercontent.com/ILoveHAKU/dsh-dialog-fence/250edf0b.../docs/运维手册与变更记录.md
  → HTTP 200，内容里本机用户名命中 6 处
  GET https://codeload.github.com/ILoveHAKU/dsh-dialog-fence/tar.gz/<旧 tag 或旧 SHA>
  → 同样可取
  ```

  GitHub 对不可达对象不立即回收，只要知道 SHA 就能取。而我当时已经把仓库转成 public，所以旧对象里的本机用户名处于**真实匿名暴露**状态。

- **我的判断错误在哪**：上一节「匿名复验」验的是「新 clone 的 worktree 与 `master` 历史 0 命中」——**这两个都成立，但都不足以证明远端干净**。缺的那一问是「旧 SHA 还在不在」。教训可以一般化成一句：**验证「已经清除」时，必须去取那个本该消失的东西，而不是只验证「留下的东西是干净的」。**

- **立即止血**：`gh api --method PATCH repos/.../dsh-dialog-fence -F private=true`，再匿名取 repo 页面 → **HTTP 404**，暴露停止。这一步可逆，先做。

- **最终处置**：GitHub 上不可达对象没有自助删除入口（只能走 Support 请求回收）。所以采用**删库重建**：删掉整个仓库，用同一名字重新建、重新推。这样旧对象的 SHA 只存在于旧仓库里，随删除一起消失。

  重建清单（删之前必须先读出来，否则会丢配置）：

  | 项 | 值 |
  |---|---|
  | description | `Dialog fence for DSH / DSH Desktop: per-conversation behavioral rule fence injected into runtime context without breaking prompt cache` |
  | topics（8） | `context-engineering` `deepseek-harness` `dsh` `dsh-plugin` `javascript` `llm-agent` `plugin` `prompt-cache` |
  | has_issues / has_discussions / has_projects / has_wiki | true / **true** / true / false |
  | 默认分支 | `master` |
  | actions/permissions | `allowed_actions: all`、`enabled: true`、`sha_pinning_required: false` |
  | default_workflow_permissions | `read` |

  `has_discussions` 特别容易漏：`.github/ISSUE_TEMPLATE/config.yml` 的 `contact_links` 指向 Discussions，不开启就是死链。

- **重建后必须重新验证的六件事**（缺一不可）：①匿名 `git -c credential.helper= clone` 成功、②worktree + 全部历史 0 命中、③**旧 SHA 匿名取必须变成 404**（这才是「真的没了」的判据）、④CI 跑绿、⑤分支保护重新配上 `test`、⑥五套测试在干净克隆里全绿。

**⑨ 重建之后又发现裸名：为什么这事做了两遍**

第一轮重建并转 public 之后，用一条**独立于扫描器**的宽面检索复核远端（大小写不敏感，遍历每个 commit 的每个 blob，模式＝本机名 + 本机 hostname + 内部对话编号 + 真实 session id 前缀 + 本机用户名后半），命中 **1 处**——而扫描器当时是绿的。

- **根因是扫描器的规则太窄，不是搜索没做**：`real-name` 第一版要求「名 + 可选分隔 + 姓」，于是文档里一句「只查了本机名（裸名形态）与 hostname」里的**裸名**被放过。而那句话恰好把本机名写成了明文。**这是典型的「为了记录一个教训，把教训本身写了进去」。**
- **强度差别**：宽面检索用 `-i` 且只匹配名本身，比规则宽；规则宽还是窄，只有拿更宽的检索去对撞才能发现。所以「扫描器绿 + 人工再看一眼」不是冗余，是两层不同强度必须互相对撞。
- **修法**：`real-name` 放宽到只匹配名（`\b<名>\b`，大小写不敏感），另加一条 `real-name-surname` 匹配「姓-IT」形态（不单匹配常见姓，避免误报）。**必须做反向验证**：临时造一个含裸名的文件 → 扫描器变红 → 删掉 → 转绿。两侧读数都留了（红：`[real-name] <探针文件>:1  <本机名>`；绿：`0 处命中`）。

修完后重做一遍完整流程（因为第一轮重建的仓库里那一处已在 master 历史内）：

1. 全历史 `--tree-filter` 扫掉裸名。**16 个 commit 里只有 2 个变了**（引入该词的那两个），其余 SHA 原样不动——`filter-branch` 对未变化的树会复用原 commit，这正好可以当「改动范围是否正确」的判据。
2. 在 `%TEMP%` clone 里**先干跑**一遍（同样 16 commit / 9 tag、全历史 0 命中、五套测试全绿）再对真实仓库执行。
3. **第二次删库重建**：旧仓库删掉 → 同名新建 → 推 master + 9 tag → 重配 description / topics / `has_discussions` → 转 public → 重配 master 保护。
4. 复验（本次全绿）：匿名 `clone` 成功；16 commit / 9 tag / 25 文件；worktree 与**全部历史** 0 命中；**commit message 0 命中**；旧 SHA 三个（`0c8da4d` / `382bd2b` / `250edf0`）在 `raw` 与 `.patch` 两条路径上**全部 404**，而当前 HEAD 的 `raw` 是 200（这条对照才排除「URL 拼错导致全 404」）；CI `success`。

> 教训合并成一句：**删库重建不是「做一次就完了」的动作，它是一个需要复验闭环的发布步骤。** 第一轮验证通过不等于内容真的干净——第一轮验的是「我知道的那些形态」，第二轮才发现「我不知道的那种形态」。

### 2026-10-26 · v0.12.1「某个对话的额外规则」卡片拆成两行

**起因**（用户 CR-20，原话）：

  第一行 `对话` 标签 + 下拉；第二行 `停用/启用该对话` 按钮 + 计数。
- `.dialog-fence-select` 改为 `flex:1; min-width:0`（去掉固定 min/max-width），宽度跟着卡片走。
- 新增 `.dialog-fence-picker` / `.dialog-fence-picker-row` / `.dialog-fence-count` / `.dialog-fence-label`
  四条 CSS；按钮与计数都是 `flex:none; white-space:nowrap`，任何宽度下都不折行。

**守它的测试**（`test/render.mjs` 新增 3.7 组，先红后绿）：

断言 `.dialog-fence-picker` 存在、`.dialog-fence-picker-row` **恰好 2 个**、
`.dialog-fence-count` 存在、计数不再是 `<span class="dialog-fence-meta" style="flex:1">N/40 条专属规则`、
下拉框 CSS 含 `flex:1`。BEFORE 红灯：

```
AssertionError [ERR_ASSERTION]: the picker gets its own two-row block
  expected: /class="dialog-fence-picker"/
```

**顺带记一条教训**：这类「中文被挤到逐字换行」的问题，`display:flex` 的单行容器 +
固定宽度子元素是最常见的成因；判断标准不是「看起来有没有换行」，而是**子元素有没有
被压到只剩一个字宽**。只看 DOM 结构断言不够，最终要靠 480px 宽度下的实拍截图确认。

### 2026-10-26 · v0.12.0 浮层与设置页合并成同一套界面

**起因**（用户 CR-19，原话）：

> 右上角的围栏的配置没有设置里的围栏配置：针对单独对话进行的单独配置，需要修改这个问题，让两边的UI和风格统一

配了两张图：设置页是四张卡片（总开关 / 通用规则 / 某个对话的额外规则 + 对话下拉 / 注入路径说明）；
右上角「围栏 14」浮层只有「通用规则」+「仅本对话的额外规则」两段裸列表，**没有对话下拉**，
底部还挂着一整条一次性工具条（添加专属规则 / 清空专属 / 打开文件夹 / 下一轮生效）。

**根因**：数据从来没分叉（两边都写同一个 `fence.json`），但**可见能力分叉**了。
0.10.0 给设置页加了「某个对话的额外规则」，浮层没跟着改 —— 它还是 0.5.0 时代那份独立实现。

#### 改法：浮层不再有自己的一份实现

`Panel` 现在只保留浮层独有的三样东西：标题、总开关状态 pill、「关闭」按钮；
卡片区直接渲染设置页那个组件：

```js
react.createElement(FencePage, {
  flat: true,                      // 紧凑版式（浮层自己已有 padding 与标题栏）
  preferredSessionId: sessionId,   // 浮层点开的是这一条对话
  useSessions: props?.useSessions, // 透传槽位标准属性，下拉才能显示对话名称
})
```

删掉的是 `Panel` 里约 110 行重复实现（自己那份通用/专属列表、两个新建 `textarea`、整条 `dialog-fence-foot`），
连同 `.dialog-fence-foot` 的 CSS 规则一并删除。`client.js` diff：`193 changed, 86 insertions(+), 154 deletions(-)`。

#### `preferredSessionId`：让浮层「点开就停在那条对话上」

设置页的默认选中是「当前对话 > 最后归档 > 第一行」，浮层要求的是「点开它的这条」。
新增一个可选 prop 即可，不必分叉：

```js
const preferred = typeof props?.preferredSessionId === 'string' ? props.preferredSessionId : '';
if (preferred !== '' && !liveIds.has(preferred) && !archivedRows.some((r) => r.id === preferred)) {
  liveRows.push({ id: preferred, label: '当前对话' });
  liveIds.add(preferred);
}
```

优先级：**手选 > `preferredSessionId` > 当前对话 > 最后归档 > 第一行**。
「不在候选里就补一条」是必须的：浮层刚打开时 `sessions` store 可能还没拉到数据，
不补的话下拉是空的，用户仍然改不了自己这条对话。

#### 顺带补齐：设置页也能单独停用某条对话

浮层顶部原来有「停用本对话 / 启用本对话」，设置页没有对应动作 —— 同一个能力两处不一致。
现在设置页第三张卡片的对话下拉旁也有「停用该对话 / 启用该对话」，按**该对话自己的** `enabled` 判断。

#### 测试（先红后绿）

- `test/render.mjs` 新增 3.6 段，先写断言再改代码。它用真 React 18.3.1 把
  `FencePage({flat:true, preferredSessionId, useSessions})` 当作**浮层内容**渲染，断言：
  `.dialog-fence-card`、`.dialog-fence-select`、「围栏规则（对每个对话生效）」「某个对话的额外规则（可选）」
  「添加专属规则」「停用该对话|启用该对话」「打开文件夹」全部存在；**`dialog-fence-foot` 0 命中**；
  且 `preferredSessionId` 指向第二条对话时那个 `<option>` 带 `selected`。
- `test/client.mjs` 的 textarea 计数断言从 **5 改成 3**。这个数字变小就是统一的证据：
  过去浮层自己又抄了一份新建框（+2），现在整个 bundle 只剩 1 个规则编辑器 + 2 个新建框（通用层、专属层）。
- 五套测试全部 `exit=0`：`smoke` / `route` / `client` / `render` / `opensource`。

#### 这一轮最值得记住的

**「同一份数据、两套视图」是这类 UI 不一致的结构性来源。**
只要两处各自实现一遍渲染，就会各自长出自己的默认值、自己的按钮、自己的分区 ——
哪怕它们读写的完全是同一个文件。判断有没有真正统一，看**重复实现的代码有没有被删掉**，
而不是看两处看起来像不像。

表现只是「错误文字永远是那个硬编码的红」，不跟主题、深色模式下显得刺眼。**这是最值得记住的一类坑——
用兜底值写的 CSS 变量失效是静默的。**

**怎么查出来的**（可复用）：`cordis_inspect_query(platform:'client', provider:'Theme', method:'listTokens')`

#### 修复 2：兼容性声明搬出死字段

### 2026-10-21 · v0.10.0 设置页可编辑「某个对话的专属规则」+ 浮层点外部关闭

**起因**（用户 CR-17，两条并列）：

1. 「侧面和设置里的围栏配置没有同步右上角围栏配置里的下面的自定义配置界面」——

2. 「右上角弹窗的围栏配置需要增加点击外部以后自动关闭弹窗的功能」。

#### ① 能不能不碰宿主就拿到「对话名 + 当前对话」？——能

这是本轮唯一需要先证伪的假设。查证过程（全部是 asar 内源码 + `cordis_inspect_query`）：

| 查的地方 | 结论 |
|---|---|
| client 服务目录（只有 8 个：`layout/locale/sessions/slots/theme/timer/uiWorkspace/workspaces`） | `sessions` 服务只有 `retain/using/retainInfo/search/fork/scope/binding`，**没有当前会话、没有标题** |
| `settings.section` 的 ownerProps | 只有 `{ close }`，**不含 sessionId** |
| `settings.section` 的 standardProps | **含 `useSessions`**（还有 `useResource/useWorkspaces/usePanelInfo/useSessionStatus/useSessionRetainInfo`） |
| `plugins.bundle.config` / `settings.plugins.tab` 的 standardProps | **同样含 `useSessions`** |
| host 侧的 `sessionTitle` 服务 | 存在，`get(session)` 能拿标题 —— 但**用不上**，因为客户端已经有了 |

`useSessions` 的用法实证（`@deepseek-ai/dsh-client-ui-open-in-app/lib/client.js` 里现成的写法）：
`const cwd = useSessions((state) => state.byId[sessionId]?.cwd);`

快照形状（`@deepseek-ai/dsh-api-session-controller/lib/types/client/sessions/service.js` 的 `projectList()`）：
`{ ids, byId, phase, projectionsBySession }`，`byId[id]` 含 `{ id, displayTitle, running, retainedBy, blank, updatedAt, title?, cwd?, parentId?, origin? }`。

**关键陷阱**：`displayTitleOf(title, cwd, id)` = 标题 → 项目目录名 → **原始 id**。
最后那层兜底会把 `session-<uuid>` 显示出来，正好违反 CR-18。所以界面不能无条件用 `displayTitle`，
必须有「都没有就用 `未命名对话 N`」这一层自己兜。

**「当前对话」的判据**照抄 DSH 自己的 `mainSessionId()`（`dsh-client-ui-workspace/lib/client.js`）：
`Object.values(list.byId).find((s) => (s.retainedBy.mainView ?? 0) > 0)?.id`。

**结论：`index.js` 一行未改。** 这条结论是有代价的——如果三个槽位里任何一个当时没给 `useSessions`，
就只能退回「宿主新增一个只读动作」的方案（`sessions.list()` + `sessionTitle.get(session)` 拼列表，
并且在 `fenceTextFor` 里记录最近活跃 id）。所以代码里保留了「`props.useSessions` 不是函数就退化成不显示选择器」
的降级分支，不让界面崩。

#### ② 为什么 `<option>` 的 value 用下标而不是 sessionId

因为有一条现成的界面约束在守：`test/render.mjs` 断言设置页渲染结果里**不得出现** `session-[0-9a-f]{8}-`
（这条断言是 0.6.0 为「设置页不展示 sessionId」加的）。如果 `<option value={sessionId}>` 就当场违反。
用下标还有个副作用是好的：用户复制 DOM 也拿不到 id。

#### ③ 点外部关闭为什么不能简单地 `document.addEventListener('click', ...)`

三个坑，全部踩过：

1. **必须用 `mousedown` 而不是 `click`**：`click` 要等按下+抬起，而面板里按钮的 `click` 会先执行，
   如果关闭逻辑依赖抬起顺序，会出现「点了按钮既执行又关闭」的竞态。`mousedown` 在按下瞬间判定，语义更稳。
2. **必须排除右上角那个触发按钮**：它自己的 `onClick` 是 `toggle`。若按下时判成「外部 → 关闭」，
   紧接着它的 `onClick` 又把面板打开，等于这个按钮失效。代码里显式判断目标的 `closest('.dialog-fence-trigger')`。
3. **必须用捕获阶段 + `ref.contains()`**：面板是 `position: fixed`，不在触发按钮的 DOM 子树里；
   用捕获阶段能保证在任何子组件的 `stopPropagation` 之前拿到事件。

测试上这条不能靠「读源码里有没有 `addEventListener`」来验——`test/client.mjs` 用一个**真的会调回调**的
`useEffect` 桩把 Panel 挂起来，然后手工派发 `document` 上的 `mousedown`，断言三种情况（面板内不关 /
面板外关闭 / 触发按钮上不关）以及卸载时监听被移除。

### 事故 1（已修复）：PowerShell 写坏 rules.json → 围栏静默消失

**经过**：用 `$state | ConvertTo-Json | [System.IO.File]::WriteAllText(...)` 写规则文件，中文被按 GBK/UTF-16 落盘，最终写成 **0 字节**。插件 `JSON.parse` 抛错 → 被最外层 `catch` 吞掉 → 返回空串 → 围栏无声消失，无任何报错（这次 fail-safe 反而得到真实验证）。

**修复**：`loadState()` / `readRuleFile()` 都改为读 Buffer 后自动探测编码（含 `\u0000` 判定 UTF-16LE），并去掉 BOM；解析失败时 `console.warn` 一次（按 mtime+size 去重，不会刷屏）。

**回归**：`test/smoke.mjs` 断言「UTF-8 带 BOM」与「UTF-16LE」的 `state.json` 与规则文件都能正确读。

**隔离修复**：冒烟测试原先直接读写线上规则文件，测试中途崩溃就会弄丢真实规则。现改为 `DIALOG_FENCE_DIR` 指向 `mkdtemp` 的一次性沙箱，结尾断言沙箱已删、线上目录未被写脏。

**教训**：写含中文的 JSON 一律用 node 或编辑器，**不要**用 PowerShell `ConvertTo-Json + WriteAllText`。

### 事故 2（已知限制）：`dsh-hmr` 不重载本插件

**实测证据**：编辑 `index.js` 加入 UTF-16LE 兼容后，把规则文件写成 UTF-16LE —— 若新代码生效，围栏应显示 `HMRTEST` 规则；实际快照里**围栏整段消失**，说明运行的仍是旧代码。触摸文件时间戳后再试一次，结果相同。

**结论**：改插件代码（`index.js` 与 `client.js` 都算）必须重启 DSH Desktop。`cordis.patch.yml` 里那行 `hot reloads via dsh-hmr` 注释对本插件不成立。

### 实测 3：单变量缓存实验（围栏改动不破坏前缀缓存）

在其余条件不变的前提下，追加一条规则后立刻观测下一次真实请求：

```
#484  10:31:23  input=111.5K  cached=108.4K  hit 97.2%  new=2729  comp=0  ttl=337
```

`ttl=337` 是本次唯一可归因于「围栏文本变化」的 re-bill 量，`new=2729` 是正常的新增对话内容。**围栏改动 ≈ 追加 337 token，不产生前缀重写。**

对照：同期两条 `[cache-seam] mid-history` 告警（`#408` message[3]、`#478` message[46]）与围栏文本变化时刻重合，但根因是 billion-context 自己的 strict-echo 改写：

```
02:28:31 strict-echo: injected blank reasoning_content on 3 assistant tool-call message(s)
02:29:38 ... on 5 ...
02:30:34 ... on 6 ...
```

它不断往**历史 assistant 消息**里补空 `reasoning_content`，每补一条就产生一次 mid-history 偏移。围栏注入发生在消息数组**尾部**，不可能是 message[3] / message[46] 的成因。

另外，`bili.log.old` 里在插件存在**之前**就有 9 条同类 cache-seam（跨 2026-09-30 ~ 10-15 的多个历史会话），进一步排除本插件。

**总账**：本会话 484 次请求，命中率 **95.7%**，折叠净收益 +233.99M token。

## 六、发布到社区清单（awesome-dsh-plugin）/ Getting listed on awesome-dsh-plugin

本插件已提交：[PR #9530](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/pull/9530)，

### 6.1 清单只收「一个插件一个 YAML」

字段白名单：`url` / `name` / `category` / `description` / `icon` / `tarball`（`file` 由脚本补）。
`name` 必须与 `url` 的 `owner/repo` 一致，文件名必须写成 `<owner>__<repo>.yml`。
两个 README 由 `scripts/generate-readme.mjs` 生成，**不要手改**——手工编辑 README 是「改动落到邻居条目」
的常见事故源，也是清单改成一条目一文件的原因。

### 6.2 会被 CI 直接拒的几个点（我们都逐条实测过）

| 门槛 | 实测依据 |
|---|---|
| `package.json` 必须有 `dsh.bundle` | 只有 `dsh.client` 会被判 `declares only dsh.client — that alone is not installable`，是最常见拒因 |
| 仓库创建满 1 天 | `scripts/check-submission.mjs` 的 `MIN_AGE_DAYS = 1`；不达标只提示「等约 N 小时，会自己重跑」，不用重提 |
| 仓库带 `dsh-plugin` topic | 人工/CI 检查项 |
| 描述属实 | 维护者会读源码核对，夸大是打回主因 |
| PR 最多 3 条、不得改他人条目 | `MAX_ENTRIES_PER_PR = 3`；gate 会列出 PR 动过的每个既有条目 |

### 6.3 条目里的 `icon` 与 `package.json` 里的 `icon` 不是一回事

条目 `icon:` 只接受**GitHub 托管的位图**（`ICON_HOSTS` 限定 `raw.githubusercontent.com` /
`user-images.githubusercontent.com` / `camo.githubusercontent.com` / `github.com`，扩展名限 `.png/.jpg/.jpeg/.webp`）。
**SVG 会被拒。** 本仓库 `package.json` 的 `icon: "./icon.svg"` 只影响 DSH 自己的插件页，不能直接搬进条目；
不写条目的 `icon` 就回退作者头像。约 96px 方形最佳。

### 6.4 收录 ≠ 市场能搜到（两份目录别混）

| 目录 | 生成方式 | 是否收 GitHub-only 条目 |
|---|---|---|
| `https://awesome-dsh-plugin.com/plugins.json` | 直接由 `data/plugins/*.yml` 生成 | **收** ⇒ 收录合并后 `dshmarket`「插件市场」就能搜到 |
| `https://awesome-dsh-plugin.com/index.json` | `scripts/build-index.mjs` 从 `data/npm-map.json` + npm packument 生成 | 只收有 npm 包的条目；`no npm package` / `no version` / `no publish time` 都会被 skip |

`npm-map.json` 由 `scripts/probe-npm.mjs` 生成，规则是：读仓库 `package.json` 的 `name` →
查 registry → **`repository` 字段必须指回同一个 GitHub 仓库**才登记。
所以「发了 npm 但 repository 没写对」会被静默跳过。本包 `repository` 已指向本仓库。

### 6.6 提交 PR 的最省事路径（不 clone 大仓库）

清单仓库有近 7000 个条目文件，本地 clone 很重。用 GitHub contents API 更快：

1. `gh repo fork awesome-dsh-plugin/awesome-dsh-plugin --clone=false`
2. `POST /repos/<me>/awesome-dsh-plugin/git/refs` 建分支（**必须先建分支：PUT contents 指向不存在的分支会直接 404 `Branch ... not found`**）
3. `PUT /repos/<me>/awesome-dsh-plugin/contents/data/plugins/<owner>__<repo>.yml`（`content` 用 base64，带 `branch`）
4. `gh pr create --repo awesome-dsh-plugin/awesome-dsh-plugin --base main --head <me>:<branch> --body-file ...`

### 6.7 踩过的坑

- **README 手改会导致 PR 相撞**，且 gate 有专门一步 `READMEs match data/plugins` 会红。
- **`description` 含 `": "`（冒号+空格）必须加引号**，否则 YAML 解析失败；这是描述里最常见的手滑。
- `gh api --jq` 里写复杂表达式容易先被 PowerShell 解析（`function not defined: success/0`）——复杂 JSON 处理一律先存文件再 `ConvertFrom-Json`。
- 用 `Get-Content | ConvertFrom-Json` 读 2.8 MB 的 `index.json` 会卡住两分钟以上，用 `Select-String` 直接搜字符串。
- `git clone --sparse` 之后 `git sparse-checkout set <非 cone 路径>` 会让目录不落地；先 `git sparse-checkout init --cone`。

## 七、发版到 npm（trusted publishing，无 token）/ Publishing to npm

### 7.1 为什么不用 `npm publish` + token

本机**没有系统 npm**（只有 pnpm），自举的 npm CLI 在 `%TEMP%\npmboot`；
`~/.npmrc` 里只有一行空值的 `//registry.npmjs.org/:_authToken=`，
`npm whoami` 直接 `E401`。长期存 token 既违反本项目的凭据规则，也会在换机器时失效。

所以改用 npm 的 **trusted publishing**：GitHub Actions 用 OIDC 身份向 registry
换一次性凭据，仓库里**一个密钥都不放**。

### 7.2 三件事的先后顺序（顺序错了会白做）

1. **先在 npmjs.com 配好 Trusted Publisher**（包 → Settings → Trusted Publisher →
   GitHub Actions，Owner `ILoveHAKU` / Repository `dsh-dialog-fence` /
   Workflow `publish.yml`）。这张表单**两天内**必须完成首次发布，否则过期。
2. 再推 `v*` tag —— 这一步才真正触发 `publish.yml`。
3. 发布后去 registry 核对 `dist-tags.latest` 与 tarball 的 `shasum`。

**首次发布有个前提**：包必须已经在 registry 上存在过一次（或用
`npm publish --access public` 首发了 0.11.0 那种方式建过包），
OIDC 的 trusted publisher 是**挂在已存在的包**上的配置。本包 0.11.0 已发布，满足。

### 7.2.1 项目既定规则：改完就发，两边不留版本差

用户 2026-10-26 明确要求：**默认每次改完都要发 npm，仓库与 npm 必须保持同步。**

这条规则的由来是一次真实的不一致：0.12.0 发到 npm 后，仓库又推了 0.12.1
（CR-19 的「按钮挤成一行」修复），但没打 tag，结果是仓库 0.12.1 / npm 0.12.0，
按 README 用 `npm i dsh-dialog-fence` 装到的人拿到的是没修 UI 的那个版本。

执行口径：

- **升版本**（`package.json`）+ **写 CHANGELOG** → **提交推送** → **打 `v*` tag 推送**，
  一件都不能省。只做前两步，npm 上不会有任何变化。
- 每次 push 前后用三条命令确认同步，任一条不一致就算没发完：

  ```bash
  git describe --tags --abbrev=0                 # 仓库最新 tag
  node -p "require('./package.json').version"    # 仓库版本
  npm view dsh-dialog-fence version              # registry 上的 latest
  ```

- 仓库领先 npm 时**补推 tag 即可**，不需要重新提交代码；tag 一推，`publish.yml`
  会自己跑测试、打包、发布、留档。
- 例外只有一个：改动完全不涉及已发布内容（例如只改 `.github/`、只改 `test/`、
  只改 `probe/`）时可以在 PR 描述里写明「无版本变更」，但仍需在 CHANGELOG 记一行，
  避免下一个人以为漏发。

### 7.3 版本门槛（硬性）

> Trusted publishing requires npm CLI version 11.5.1 or later and Node version 22.14.0 or higher.

workflow 里钉 `node-version: '24'` + `npm install -g npm@latest`，并在发布前打印
`node --version` / `npm --version` 留证。

### 7.4 `publish.yml` 做了什么

`checkout`（**`ref: inputs.publish_ref || github.ref`**，`fetch-depth: 0`）→
`setup-node`（node 24 / **不设 registry-url** / `package-manager-cache: false`）
→ 清掉任何残留凭据 → 打印 node 与 npm 版本 → `npm install -g npm@latest`
→ **校验 tag 与 `package.json` 版本一致**（不一致 `::error::` + `exit 1`）
→ `npm test` → OIDC 环境自检 → **查这个版本是否已发布**（已发布则整步跳过）
→ `npm pack` + `npm publish ./dsh-dialog-fence-*.tgz --access public`
→ `upload-artifact` 留档 tgz。

两个细节值得记住：

- **先 `npm pack` 再发那份 tgz**，而不是直接 `npm publish`。因为直接 publish
  之后工作区没有 tarball，`upload-artifact` 的 `path: '*.tgz'` 会**静默跳过**
  （`if-no-files-found` 默认就是 `warn`）。先 pack 还顺带保证「留档的那份」与
  「发上去的那份」字节一致。
- **`upload-artifact` 的 `if-no-files-found` 显式写成 `error`**，让「没找到包」
  变成红灯而不是警告。

发版只有两条路，但**优先走 tag**：

| 方式 | 何时用 | 注意 |
|---|---|---|
| 推 tag `v*` | 正常发版，**推荐** | checkout 自然拿到 tag 指向的 commit，溯源天然成立 |
| 手动 `Run workflow` | 只想重跑一次失败的发布 | **必须填 `publish_ref`**（如 `v0.12.0`），否则 checkout 拿到分支 HEAD，发出去的东西可能不是 tag 指向的那份（见坑 5） |

### 7.5 红线由测试钉住，不靠自觉

`test/release.mjs` 是纯静态断言（零依赖，读文件而已），检查 13 组：

1. `.github/workflows/publish.yml` 存在；
2. 触发是 `push: tags: ['v*']` + `workflow_dispatch`；
3. `permissions` 同时有 `id-token: write` 与 `contents: read`；
4. `node-version` ≥ 22、**不得**设 `registry-url`、`package-manager-cache: false`；
5. 有 `npm publish`，且显式带 `--registry https://registry.npmjs.org`；
6. **红线**：workflow 生效代码里不得出现 `secrets.` / 字面 `_authToken = <值>`；
   `NODE_AUTH_TOKEN` **只允许**出现在 `unset` 或"探空"语句里（见下方坑 3）；
7. `npm test` 存在且**在** `npm publish` 之前；
8. 有 tag 与 version 一致性校验，且用 `GITHUB_REF_TYPE` 区分手动触发；
8b. 手动触发必须能传 `publish_ref`、checkout 必须用它、且发布前要验证 HEAD
   就是那个 tag（坑 5）；
8c. 发布前必须先问 registry「这个版本存在吗」，并用 `GITHUB_OUTPUT` 把结论
   交给后续步骤当 gate（坑 6）；
9. `package.json` 无 `private`、version 合法 semver、`repository.url` 指回本仓库；
10. `files` 白名单不含 `fence.json`（用户数据）与 `assets/`（截图）；
11. 三个官方 action 的主版本不得低于 node24 门槛（checkout≥v5、setup-node≥v5、upload-artifact≥v6）。

**坑 1（已踩，第一版就红）**：第 6 条最初直接扫整个 workflow 文本，而 workflow 的
注释里写着「不需要 NPM_TOKEN」这句说明，于是被自己的注释判红：

```
AssertionError [ERR_ASSERTION]: publish workflow has no NPM_TOKEN / NODE_AUTH_TOKEN reference
```

修法是先把**注释剥掉**再扫：

```js
const wfCode = wf.split('\n').map((line) => line.replace(/(^|\s)#.*$/, '$1')).join('\n');
```

红线针对的是「生效的配置」，不是「文档里提到这个词」。同理，`npm test` 与
`npm publish` 的先后比较也必须**两边都用 `wfCode`**——曾因一处用原文
`wf.indexOf('npm publish')`、另一处用 `wfCode` 而误报 `tests run before npm publish`。

**坑 2（已踩，CI 真实失败）**：`setup-node` 一旦设了 `registry-url`，它就会往
`~/.npmrc` 写一行 `_authToken=${NODE_AUTH_TOKEN}`。npm 只要发现存在 `_authToken`
就改走 token 鉴权、**不再做 OIDC 交换**，trusted publishing 直接失效。实测现象：

```
npm error 404 Not Found - PUT https://registry.npmjs.org/dsh-dialog-fence
```

这个 404 还会掩盖「Trusted Publisher 根本没配」的真实原因，极难查。
正确做法：**不设 `registry-url`**，改为在 `npm publish` 上显式 `--registry`。

**坑 3（已踩）**：为清掉 `setup-node` 注入的 token 而写 `unset NODE_AUTH_TOKEN`，
会被「红线 6」判红——因为那条断言原本是「全文不得出现 `NODE_AUTH_TOKEN`」。
断言要收窄成「只允许出现在 `unset` / 探空语句里」，而不是禁止提及这个名字。

**坑 4（已踩，见 run 页 annotation）**：官方 action 钉在 `@v4` 会有两条真实告警：

```
Node.js 20 is deprecated. The following actions target Node.js 20 but are being
forced to run on Node.js 24: actions/checkout@v4, actions/setup-node@v4

Unexpected input(s) 'package-manager-cache'
```

`setup-node@v4` **根本没有** `package-manager-cache` 这个输入（v5 才加），
所以写了会被静默忽略——**CI 绿，但缓存其实没关**。统一升到
`checkout@v6` / `setup-node@v6` / `upload-artifact@v6`（都是 node24）即可，
第 11 组断言就是防止将来又被降回 v4。

**坑 5（已踩，0.12.0 真实事故）**：手动触发会发出「不是 tag 那份」的内容。

事故过程：`v0.12.0` tag 打在 commit `6ad7961` 上，之后又推了 3 个 commit 才想起发版，
于是用手动 `Run workflow` 触发 —— 而手动触发 checkout 的是**分支 HEAD**（`e2f9c42`）。

后果不是「报错」，而是**静默地发错东西**：

```
npm 上的 provenance.resolvedDependencies  ->  ...@e2f9c42   ← 实际发布的 commit
git rev-list -n 1 v0.12.0                 ->  6ad7961        ← tag 指向的 commit
```

两者不一致，于是**按 tag 重新打包会得到另一个 shasum**，tag 从此失去溯源意义。
实测核对（下载 registry 上的 tgz 解包，逐文件比 git blob hash）：

| 文件 | tarball | vs `e2f9c42` | vs `6ad7961` |
|---|---|---|---|
| 代码类 9 个 | — | 全部相同 | 全部相同 |
| `README.md` | `3f83fd0f` | **==** | != |
| `docs/运维手册与变更记录.md` | `600249fb` | **==** | != |

即代码一模一样、只有两个文档不同 —— 所以**光看功能是发现不了的**，必须比 blob。

修法（本轮已做）：
1. `workflow_dispatch` 增加 `publish_ref` 输入，checkout 用
   `ref: ${{ inputs.publish_ref || github.ref }}`，并 `fetch-depth: 0`；
2. 发布前用 `git rev-list -n 1 <tag>` 与 `git rev-parse HEAD` 比对，不等就 `::error::`；
3. 不填 `publish_ref` 时只打 `::warning::` 放行（保留「就想发当前分支」的可能），
   但把「应当填」写进提示。

事后订正：把 `v0.12.0` 重新指到真正被发布的 `e2f9c42`，并用 CI 复算验证 ——
在 `e2f9c42` 上 `npm pack` 得到的 shasum 是
`d556063b7dfd08272a7f0b6ae1d1f3192393d4c4`，与 registry 上的完全一致。

**坑 6（已踩）**：移动 tag 会重新触发 workflow，而该版本已经在 registry 上了。

`git push --force` 一个 `v*` tag 会再跑一次 publish，此时 `npm publish` 必然
`E403 You cannot publish over the previously published versions: 0.12.0`，
于是「修正 tag」这种纯文档性动作也会产生一封失败通知。修法：发布前先
`npm view <pkg>@<version> version`（存在时 exit 0，不存在时 `E404` exit 1），
把结论写进 `GITHUB_OUTPUT`，让发布与留档两步都用 `if:` gate 住。

顺带一个反直觉现象：那次 tag-move 触发的 run **仍然跑了旧逻辑并失败**，
因为 workflow 定义本身取自 checkout 出来的 commit（即 tag 指向的 `e2f9c42`），
而不是分支上最新的 `.github/workflows/publish.yml`。**改 workflow 后想让它生效，
必须先让 tag 指向含新 workflow 的 commit，或者走分支上的手动触发。**

### 7.6 OIDC 通了但发布仍失败：看懂 `package not found`

先做 OIDC 自检（workflow 里已有这一步），**只报存在性、不打印令牌**：

```
ACTIONS_ID_TOKEN_REQUEST_URL: present
ACTIONS_ID_TOKEN_REQUEST_TOKEN: present
```

两个都是 `present`，说明 `id-token: write` 已生效、OIDC 链路没问题。
此时若 `npm publish` 仍失败，用 `--loglevel verbose` 看真实原因：

```
npm http fetch POST 404 https://registry.npmjs.org/-/npm/v1/oidc/token/exchange/package/dsh-dialog-fence
npm verbose oidc Failed token exchange request with body message: OIDC token exchange error - package not found
npm error code ENEEDAUTH
```

**`package not found` 不代表 npm 上没有这个包**（`Invoke-RestMethod` 能取到
`latest=0.11.0`）。

实测依据：这句话不是 npm CLI 自己编的，CLI 只是把 registry 响应体里的 message
原样打出来 —— `%TEMP%\npmboot\package\lib\utils\oidc.js:198-199`：

```js
} catch (error) {
  log.verbose('oidc', `Failed token exchange request with body message: ${error?.body?.message || 'Unknown error'}`)
```

也就是说 `OIDC token exchange error - package not found` 是**registry 侧**对
`POST /-/npm/v1/oidc/token/exchange/package/dsh-dialog-fence` 的答复。

**结论（已由实验证实）**：这个 404 指的是「本仓库 + 本 workflow 没有为该包
配置 Trusted Publisher」，而不是「包不存在」。

原先只写成推断，后来做了一次证伪实验，结论成立：

| 阶段 | Trusted Publisher | 同一 workflow 的结果 |
|---|---|---|
| 第一次 | 未配置 | `POST .../token/exchange/package/dsh-dialog-fence` → **404**，`OIDC token exchange error - package not found`，`npm error code ENEEDAUTH` |
| 第二次 | 配好（`ILoveHAKU/dsh-dialog-fence` + `publish.yml`） | `POST .../token/exchange/package/dsh-dialog-fence` → **201**，`npm verbose oidc Successfully retrieved and set token`，`PUT` → **202**，`+ dsh-dialog-fence@0.12.0` |

两次唯一的变量就是那个网页配置，其余（commit、workflow、npm 版本、Node 版本）完全相同。
所以「包不存在」是误导性措辞：包一直在 registry 上（`latest=0.11.0` 当时就能取到）。

排查顺序：
1. 确认 `/-/package/<pkg>/trust` 返回 **401**（需登录）——说明这段配置只能在网页做，
   命令行 `npm trust list` 同样会 401；
2. 去 npmjs.com → 包 → Settings → Trusted Publisher，核对三格：
   Owner `ILoveHAKU` / Repository `dsh-dialog-fence` / Workflow **`publish.yml`**
   （是文件名，不是 workflow 的 `name:` 字段）；
3. 注意手动 `workflow_dispatch` 触发时，校验用的仍是**配置里那个 workflow 文件名**；
4. 配置有有效期：填完**两天内**必须完成首次发布，否则作废需重配。

配好之后页面上会显示 `Status: Pending validation` 并提示「Publish once before
<日期> to validate this configuration」——**这是正常的中间态**，首次发布成功才会转正。

一个排查陷阱：`gh run view --log` 里的发布步骤要一直读到**最后几行**才有结果。
`npm notice` 会先打一大段 tarball 清单，`npm info ok` 才是终点。我第一次只看了
前半段就以为没发出去，实际上 `PUT 202` 已经成功——registry 的读缓存还有几分钟延迟，
直接查 `dist-tags` 仍是旧版本，加 `?ts=<时间戳>` 破缓存才看到 `0.12.0`。

### 7.7 本机核对 registry（不需要凭据）

```powershell
$m = Invoke-RestMethod https://registry.npmjs.org/dsh-dialog-fence
$m.'dist-tags'.latest                                # 期望 0.12.0
$m.versions.'0.12.0'.dist.shasum                     # 与 npm pack 报的 shasum 对照
$m.versions.'0.12.0'.repository.url                  # 应包含 ilovehaku/dsh-dialog-fence
```

`repository.url` 这一条不只是好看：awesome 的 nightly `probe-npm.mjs` 判据是
`repoField.toLowerCase().includes(repo.toLowerCase())`，对不上就**进不了
`index.json`**（也就进不了 Discover）。

### 7.8 `npm publish --dry-run` 能过 ≠ 能发布

dry-run 完全不校验凭据。用空 `_authToken` 也能过。**不要把 dry-run 的绿灯
当成发布能力证明**——真正的判据只有 registry 上的 `dist-tags` 是否变了。
