# dialog-fence 设计与实施方案

> 会话级「围栏」插件：给**每一次对话**设定边界与行为约束，规则可随时增删、下一轮即生效，且**不破坏前缀缓存、不膨胀上下文、不影响其它对话**。
> 本文档记录最终方案、每一条设计红线的源码级依据、以及被否决过的替代路线。

- 版本：0.4.0（0.1.0 = 宿主半边；0.2.0 = 追加浏览器面板 + 双形态安装；0.2.1 = 修正 `dsh.client.inject`、补真 React 渲染测试；0.3.0 = 每条规则独立 txt + 插件页 + 修复 404；**0.4.0 = 设置左栏一级菜单 `settings.section` + 插件页卡片 `plugins.item`**）
- 落地日期：2026-10-20
- 代码：
  - `harness/dialog-fence/index.js`（宿主半边，约 640 行，零 import）
  - `harness/dialog-fence/client.js`（浏览器半边，约 23 KB，手写懒 CJS 工厂，只 `require('react')`）
- 状态与数据：
  - `harness/dialog-fence/rules/state.json` —— 只存开关（`{version:2, global:{enabled}, sessions:{<id>:{enabled}}}`）
  - `harness/dialog-fence/rules/sessions/<sessionId>/NN-<slug>.txt` —— **每条规则一个文件**，文件内容即规则正文
  - `DIALOG_FENCE_DIR` 可把整个 `rules/` 指到别处（测试用）
- 挂载点：`harness/profiles/web/cordis.patch.yml` 的 `- insert: [- id: dialog-fence ...]`（由 `scripts/install.mjs` 维护，行号随补丁层增长而变，不要按行号定位）

## 1. 需求与红线（来自用户 CR-01）

| # | 要求 | 本方案的兑现方式 |
|---|---|---|
| 1 | 不影响 DSH Desktop 其它对话 | 规则按 `sessionId` 分桶，只有显式 `on` 的会话才渲染文本；未登记会话渲染**空字符串**，而 `renderContextSections()` 会 `.filter(s => s.text.length > 0)` —— 空串 = 零 token、零注入、零副作用 |
| 2 | 不破坏缓存命中 | 只注册 `systemPrompt.context()`（运行时上下文段），**绝不碰系统提示词段**；运行时快照由 agent-loop 以「纯追加一条 user 消息」落历史，已有请求前缀永不被重写 |
| 3 | 尽可能省上下文 | 快照文本不变时 `RuntimeContextProjection.project()` 直接 `return`（一条都不追加）；变了才追加一份新快照；渲染有 40 条 / 2400 字符硬上限 |
| 4 | 与已装的主动压缩插件 billion-context 共存 | 注入落在 `Current runtime context` 快照里 → 被其 `dshDurableToolPath` 归类为 `durable/runtime-context` → 自动进 `protectedLatestTools`，只保最新一份，旧快照照常被压缩 |
| 5（CR-03） | 每条规则单独一个 txt，不要 textarea | 存储从单个 `rules.json` 改为 `rules/sessions/<sessionId>/NN-<slug>.txt` 目录；`state.json` 只存开关。UI 侧全部改成**单行 `<input>` 内联编辑**，`client.js` 里不存在 `createElement('textarea')`（有测试断言） |
| 6（CR-03） | 在 dsh 与 dsh desktop 的插件页出现且能开关 | 客户端在 `settings.plugins.tab` 注册自有 tab（id `dialog-fence` / order 50 / label「对话围栏」），页内含全局总开关 + 会话清单；插件行的 loader 开关本身由 `pluginManager.setPluginEnabled` 提供（我方条目有 `patchId`、无 `readOnlyReason` ⇒ 可切） |
| 7（CR-03） | 面板左下角 `HTTP 404` | 根因是 `ctx.get('connection')` 在 `apply()` 时刻返回 `undefined`（cordis 的 `get()` 默认 `strict=true`，只返回 provider fiber 已 ACTIVE 的服务）→ 整段 `connection.fetch.register` 被静默跳过 → 请求落到 `createSharedFetchHandler` 的兜底分支返回 `new Response("not found",{status:404})`。改为 `ctx.inject(['connection'], cb)` 后修复 |

## 2. 最终架构

```
五处界面（client.js）              /fence 命令（任意形态）      直接编辑 txt 文件
  conversation.session.header.utilities                     │
  + shell.overlay 浮层 + settings.section 设置页  │           │
  + plugins.item 插件卡片 + settings.plugins.tab  │           │
        │  fetch("api/dialog-fence")           │           │
        ▼                                      ▼           ▼
  host: connection.fetch.register   ctx.commands.register   fs
  { path:'/api/dialog-fence' }      { name:'fence' }         │
        └──────────────┬───────────────────┘                │
                       ▼                                     ▼
        rules/state.json（开关） + rules/sessions/<id>/NN-*.txt（正文）◀─┘
                                   │
                     systemPrompt.context({name:'dialog-fence:rules', order:118})
                                   │  仅当该 sessionId enabled 时返回文本
                                   ▼
        systemPrompt.assemble({agent, scope:agent})
                                   │
                     renderContextSections() → 过滤空段
                                   ▼
        joinContextSections() ──▶ "Current runtime context. This snapshot supersedes ..." + 围栏段
                                   │
                RuntimeContextProjection.project(snapshot)
                    文本与上次相同 → return（零追加）
                    文本变化      → append 一条 user/message（surfaceOp: append）
                                   ▼
              会话历史（追加在已缓存前缀之后，不重写任何旧 token）
```

三条写入口（面板 / 命令 / 手改 txt）最终都只落到同一个 `rules/` 目录，读路径唯一，因此不存在状态分叉。

### 为什么改成「每条规则一个 txt」

用户 CR-03 的诉求是「方便随时配置和维护」。单文件 JSON 的维护体验很差：需要转义换行、需要小心逗号、改一条要重写整份文件、手滑一次就整份失效（本项目真实发生过：PowerShell `ConvertTo-Json` + `WriteAllText` 把 `rules.json` 写成 0 字节）。

改成目录后：

- 一条规则 = 一个纯文本文件，任何编辑器直接改，没有语法负担。
- 增删规则 = 增删文件，天然免锁、天然幂等。
- `state.json` 只管开关，坏了也不会丢规则正文（规则靠「目录里有几个 txt」自证）。
- 文件名前缀 `01-` / `02-` 决定注入顺序（`localeCompare(...,'en',{numeric:true})` 排序）。

语义细节：

| 操作 | 行为 |
|---|---|
| 目录里有 txt 但 `state.json` 没这个会话 | **自动视为启用**（否则手放文件不生效，反直觉） |
| `state.json` 里显式 `enabled:false` | 以它为准（保留文件但不注入） |
| 全局 `global.enabled:false` | 所有会话一律零注入，文件原封不动 |
| 空文件 / 全空白 | 不算规则，跳过 |

### 关键常量

| 常量 | 值 | 依据 |
|---|---|---|
| `CONTEXT_NAME` | `dialog-fence:rules` | 避免与内建段冲突 |
| `CONTEXT_ORDER` | `118` | 内建 `CONTEXT_ORDERS` 只有 `SANDBOX_POLICY:110` / `APPROVAL_POLICY:115` / `SUBAGENT_DELEGATION:120`；围栏属策略层，插在审批之后、委派之前 |
| `MAX_RULES` / `MAX_TOTAL_CHARS` | `40` / `2400` | 硬上限防规则膨胀吞上下文（超出渲染 `(fence truncated: N/M rules shown)`） |
| 单条规则长度上限 | `2000` 字符 | 0.3.0 从 400 放宽（改成独立 txt 后单条可以更长）；`/fence add` 与 API `add`/`update` 都校验 |
| `DATA_DIR` | `<插件目录>/rules` | 可由 `DIALOG_FENCE_DIR` 覆盖（测试与多实例用） |

### 为什么文本里绝不能出现 `{{ }}`

`dsh-system-prompt` 的 `interpolate()` 解析到未注册的 `{{name}}` 会**直接 throw**：
`unknown prompt variable "{{x}}" in context "dialog-fence:rules"`。
一次抛错就毁掉整轮装配 —— 所以插件里所有渲染路径都包在 `try/catch`，异常一律降级为空字符串。

## 3. 四条候选注入通道的对比（源码实证）

| 通道 | 缓存代价 | 存活能力 | 结论 |
|---|---|---|---|
| **A. `systemPrompt.context()`（本方案）** | 文本不变 = 0；变了 = 追加一条快照（1–2k token，纯追加不重写前缀） | `durable/runtime-context` 自动保护最新一份 | ✅ 采用 |
| B. 静态系统提示段（常量 section） | 0 | 系统提示词不受压缩 | ⚠️ 只能承载「永不变化」的底座文案；规则本体不能放（会变 → 见坑 1） |
| C. 动态系统提示段 / 动态 `PromptSection` | **破坏性** | — | ❌ 见坑 1 |
| D. `agent/pre-step` 追加普通 user 消息 | 纯追加，安全 | **普通 user 消息不在任何保护表里**，离开 `preserveRecentMessages:3` 窗口即被压缩吞掉 | ❌ 需手造消息对象且有被吞风险 |

### 坑 1（最重要）：动态系统提示词会废掉整条 KV 前缀

`dsh-agent-loop` 的 `SystemPromptProjection.project(rendered, input)`：

```js
if (!input.inHistory || input.startsSeries || rendered.length === 0) {
  const updates = nodes.slice(1).filter(n => n.text !== '').map(n => this.replace(n.seq, ''));
  if (head.text !== rendered) updates.push(this.replace(head.seq, rendered));   // ← 头部重写
  return updates;
}
if (latest.text === rendered) return [];
return [{ message: createSystemMessage(rendered), intent: { surfaceOp: 'append' } }];  // ← 仅 in-history 才追加
```

`inHistory` 只有在 provider 声明 `systemPromptUpdate: 'in-history'` 时为真。全库扫描 3245 个 `.js` 后确认：

- **`systemPromptUpdate` 的唯一赋值来源**是 `@deepseek-ai/dsh-llm-deepseek` 的 `DEFAULT_MODELS`（`deepseek-flash` 条目带 `systemPromptUpdate: 'in-history'`）。
- 本会话路由 **workbuddy**：0 命中。
- **opencode-go**（`dsh-opencode-go@*`，2.1 MB bundle）：0 命中。

⇒ 在这两条路由上，任何随时间变化的系统提示词段都会触发 head 重写、KV 前缀全废。**围栏规则是必然变化的，所以它绝对不能进系统提示词。**

### 坑 2：`agent/request` 瀑布不能用于注入

Host 契约原文：「Model-visible content must use logged channels; this waterfall cannot mutate messages.」，签名返回 `LlmCallConfig { provider, model, reasoningEffort?, temperature?, maxTokens?, stop? }` —— 没有 messages / system 字段。

### 坑 3：不要在注入文本里硬塞 `Current runtime context`

billion-context 的分类器按文本包含判定，且 `protectedLatestTools` 的 `collectLatestProtected()` 对同一虚拟路径**只保最后一条**。围栏若伪装成 runtime-context 就会和真正的快照抢同一条 `path`，而真正的快照更新更晚 → 围栏那条不是最新 → **不保护 → 被折叠**。本方案让围栏成为真快照的**一个段**，天然共享同一条路径，不存在抢夺。

### 坑 4：不存在的现成机制（避免重复投入）

- `billion-context` 的 `acp_rule` / `RULES_USAGE_PROMPT`：9 个 dist bundle 里各 1 次，只有定义无引用；`rulesEnabled` 的 5 个使用点全是 `...rulesActive ? [RULE_TOOL] : []`（只注入工具定义）；本会话 manifest 里也没有该工具。**规则回注系统提示词的那一环没实现。**
- `compress.rules: true`：**plugin 模式下 inert**（仅 proxy 模式生效），本机是 plugin 形态。
- `harness/fence/`：已被 PreToolUse 钩子（`guard.mjs`）占用，那是**工具执行**级拦阻，不碰对话内容；本插件刻意用不同目录名 `dialog-fence`。
- `$DSH_HOME/AGENTS.md`：本机不存在，属可用的零代码备选（走内建 agent-instructions，`Instructions from:` 标记 → `durable/agents-md`），但权威级别低于系统提示词。

## 4. 与 billion-context 的相互作用（实测数据）

本节数据来自本会话 `GET http://127.0.0.1:18820/__bili/plugin/status?conversationId=dsh&fallback=latest`：

- `pluginAgent: "dsh"` → `durableMessageToolPaths.dsh = dshDurableToolPath` 生效路径成立（`dsh-native.js` 主动发 `x-bili-plugin: dsh` 头）。
- 压缩日志会明确写出「下一个请求必然失效的前缀量」：
  `[acp-compress-obs] shrink N% (~X/Y tok) foldPoint=mNNNNN blocks=K anchor≈A tok ... postCtx≈P → next-request cache ceiling ≥C%`，其中 `C = floor(100 * anchorTok / postCtx)`，`anchorTok = Σ active.blocks(ceil(summary.length / 4))`。
- 实测本会话缓存命中率长期 **95%+**（如 `cached=21,333,760 / input=22,241,490`）。围栏段的稳定存在不改变这个比例，因为它属于「一次追加、长期不变」的快照文本。

若将来希望围栏**永不被压缩**（连旧快照也不折叠），在 `~/.config/billion-context/billion-context.json` 写：

```json
{ "compress": { "protectedTools": ["durable/*"] } }
```

`classifiesDurable()` 一旦看到 `durable/` 前缀，就不再自动追加 `durable/*` 到 `protectedLatestTools`，而是走 `protectedTools` 的**全历史硬排除**。代价是旧快照永不折叠、上下文单调增长 —— 默认**不建议**开启。

## 5. 可视化面板与双形态安装（0.2.0 新增）

### 5.1 为什么能做，且不需要构建链

DSH 的客户端插件机制（`@deepseek-ai/dsh-client-modules`）只做两件事：

1. `locatePkgJson(loaderName, baseUrl)` 找到插件入口文件**最近的** `package.json`；对 `file:///` 路径不校验包名。
2. 读该 `package.json` 的 `dsh.client`（要求 `platform === 'web'`），再用 `exports['./client']` 定位 bundle 文件。

组装时 `buildComboScript` 只是把每个 bundle 的源码用 `";\n"` 拼起来执行 —— **bundle 就是普通 JS 文本**，形态固定为：

```js
window.__ModuleLoader__.load({
  id: 'dsh-dialog-fence',
  factory: (require) => { /* 只 require('react') */ return module.exports }
});
```

所以 `client.js` 是手写的，没有 rollup/vite/esbuild 参与，`file:///` 挂载也能带 UI。

### 5.2 数据通道：`connection.fetch` 而不是 `webServer`

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `connection.fetch.register({path:'/api/dialog-fence'})` | 自带 Connection 层的 Host/Origin 检查与 token 鉴权 | 只能在有 `connection` 服务的形态（web / Desktop）用 | ✅ 采用，**用 `ctx.inject(['connection'], cb)` 等待就绪**，缺失时整段跳过 |
| `webServer.register({kind:'exact', path})` | 所有形态都有 | 需自己防伪造请求；`(kind,path)` 冲突直接 throw | ❌ 无必要风险 |
| `harness.handle` + `host.call` | 官方 RPC | 属 **cordis 沙箱插件运行器**（UI 里现场写的插件），loader 形态的包拿不到 `harness` | ❌ 形态不匹配 |

> **0.2.x 的 404 事故（已修复）**：最初写的是 `const connection = ctx.get('connection')`。
> cordis 的 `get(name, strict = true)` 在 `strict` 下**只返回 provider fiber 处于 ACTIVE(2) 的服务**，
> `_getImpl` 里是 `if (strict && impl.fiber.state !== 2) return;`。
> 若 dialog-fence 的 `apply()` 早于 `connection` 的 fiber 激活，就拿到 `undefined`，
> 整段 `connection.fetch.register` 被 `if` 静默跳过。
> 之后浏览器请求 `/api/dialog-fence`，`HostConnectionService.createSharedFetchHandler` 查
> `this.fetchRoutes.get(pathname)` 命不中、interceptor 也是 `undefined`，
> 于是返回 `new Response("not found", { status: 404 })` —— 与用户看到的左下角 `HTTP 404` 完全吻合。
> 官方范式（`dsh-web-app/lib/index.js`）也是 `ctx.inject(["connection"], cb)`，而不是 `ctx.get` 软取。
> 现在 `test/smoke.mjs` 会断言 `registered.injected === [['connection']]`，防止回归。

客户端用 **document-relative** 路径（`"/api/dialog-fence".slice(1)`），与 `dsh-session-log-export` 完全一致。

### 5.3 槽位选择

| Slot | 用途 | 为什么 |
|---|---|---|
| `conversation.session.header.utilities` | 会话头部「围栏」按钮 | scope=session，standardProps 直接给 `sessionId` —— 正好对应"按会话隔离"；新 id 只会**新增**一格，不替换任何已发布项 |
| `shell.overlay` | 规则面板浮层 | frame-wide 浮层，在所有列之上、滚出容器之外；点开才渲染内容，关闭即零占位 |
| **`settings.section`**（0.4.0） | **设置左栏一级菜单「对话围栏」** | 设置面板左栏的页面列表（kind=list, scope=root）。现有 occupant 按 order：`general`(0) / `models`(10) / `plugins`(15) / `opencode-go`(20) / `agent-presets`(20) / `agency-agents`(20) / `market`(40) / `dsh-notify-me`(45) / `bili`(100) / `better-sidebar`(100)；我方 order 50，只新增不替换。ownerProps 只给一个 `close()`，页面自带数据源（走自有 `/api/dialog-fence`） |
| **`plugins.item`**（0.4.0） | **插件页「官方」分组里的卡片** | 插件页按已到达的客户端插件包列出卡片；契约 `PluginConfigViewProps { view: 'summary' \| 'page' }`，`registration` 只认 id/order/label，`replaceRisk: none`。现有 occupant 是官方设置页 `shell`(10) / `agent-loop`(20) / `subagent`(30) / `web-search`(40)，我方 order 50 |
| `settings.plugins.tab` | 插件页「对话围栏」标签页 | 设置 → 内置插件 里的分页列表（kind=list, scope=root）；现有 occupant 是 `mf/all`(10) / `mf/desktop-host-plugins`(20) / `mf/desktop-market-management`(30) / `dsh-market/dsh-market`(60)，我方取 order 50 插在中间，只新增不替换。0.4.0 起保留为老入口 |

五处都用 `ctx.slots.inject(slot, () => ctx.slots.register(...))` 而非直接 `register`：槽位由别的插件声明，`inject` 会等声明出现再贡献，插件卸载时自动撤销。

> 为什么用 `settings.section` 而不是 `main` + `sidebar.panellist`：后者会在左侧多出一块**常驻主面板**
> （且 `main` 的 `replaceRisk` 是 `shadows-shipped-ui`，`keyDomain` 已占 `conversation`），
> 与「一个配置页」的诉求不符。

### 5.3.1 插件页与「开关」的两层含义（容易混淆，特此记录）

DSH 插件页里能看到的「开关」其实有两种，彼此独立：

1. **loader entry 开关**（`pluginManager.setPluginEnabled(entryId, enabled)`）：把整个插件进程停掉/启动。
   来自 `plugin_manager list_plugins` / `list_plugins` 的 `enabled` 字段。我方条目为
   `{"entryId":"include:dialog-fence","moduleName":"file:///…/dialog-fence/index.js","enabled":true,"fiberPhase":"active","patchId":"dialog-fence"}`
   —— 有 `patchId`、无 `readOnlyReason`，**可切**。
2. **围栏业务开关**（本项目自定义）：`rules/state.json` 的 `global.enabled`，控制「是否往上下文里注入规则」。
   插件仍然运行，`/fence` 命令与面板照样可用，只是不注入。

插件页「对话围栏」那一页管的是第 2 种（更贴近用户语义：关掉围栏 ≠ 卸载插件）；
第 1 种在插件页原有的插件清单里，由 DSH 自己渲染。

### 5.3.2 插件页能否显示标题/描述/图标

`plugin_manager` 的每一行 meta 来自 `ctx.get('pluginPackages').metaOf(name, base)`，
其实现 `readPluginMeta(specifier, parentURL)` 第一行就是：

```js
if (barePackageName(specifier) === void 0) return void 0;
```

而 `barePackageName` 对 `file:` / 绝对路径 / `.` 开头的 specifier 一律返回 `undefined`。
⇒ **方式 A（file:/// 插入行）在插件页不会有标题/描述/图标**；方式 B（bundle 插入行的 `name` 是裸包名 `dsh-dialog-fence`）
才会去 `node_modules/dsh-dialog-fence/package.json` 读 `name` / `description` / `icon`。
本包已加 `"icon": "./icon.svg"`，且 `iconOf()` 的约束（相对路径、`.svg/.png/.jpg/.jpeg/.webp`、必须在 manifest 目录内、≤256 KiB）全部满足。

### 5.4 双形态安装

| 形态 | 做法 | 依据 |
|---|---|---|
| **DSH Desktop / `dsh <profile>`（方式 A）** | `scripts/install.mjs` 往 `<DSH_HOME>/profiles/<profile>/cordis.patch.yml` 追加带标记的 `- insert:` 块（`name: "file:///.../index.js"`） | profile 补丁层是官方支持的最后一层，`patchReload: live` |
| **作为 bundle 安装（方式 B）** | 包内 `dsh.bundle.patch: './cordis.patch.yml'` → `dsh plugin --profile <name> add <包>` 后由 `dsh-plugin-manager` 的 `reconcile()` 自动把包名 push 进 `dsh.profile.bundles`，启动时 `dsh-app-boot` 应用它 | `reconcile` 源码：声明了 `dsh.bundle` 的依赖会被自动加进 bundles；没声明的只打 warning |

注意 `desktop` 这个 profile 名被 Electron 独占（`bin.js` 的 `rejectElectronProfile` 会直接 `program.error`）；本机 Desktop 实际使用的是 **`web`** profile。

## 7. 被否决的替代设计

| 方案 | 否决原因 |
|---|---|
| 规则放系统提示词 + 每轮更新 | workbuddy / opencode-go 未声明 `systemPromptUpdate:'in-history'` → head 重写、KV 前缀全废 |
| 复用 `acp_rule` 规则层 | 0.1.202 无回注实现；本会话未暴露该工具；plugin 模式 `compress.rules` inert |
| 靠 hook 桥（`UserPromptSubmit`）每轮注入 | 每轮一条新 user 消息，`updatedInput` 还不被 honor；成本高且不可控 |
| 把规则写进 `AGENTS.md` | 可行但全局生效，会污染其它对话（违反红线 1） |
| 用 `harness.handle` + `host.call` 做面板数据通道 | 那是 cordis 沙箱插件运行器的 API，loader 形态的包没有 `harness` 对象 |
| 用 `webServer.register` 暴露 API | 需自己防伪造请求；`connection.fetch` 免费自带鉴权 |
| 用 `ctx.get('connection')` 软取服务 | 默认 `strict=true` 只返回 ACTIVE 的 provider；`apply()` 时序早于 connection 激活就拿到 undefined，路由被静默跳过 → 面板 404。改用 `ctx.inject(['connection'], cb)` |
| 复用已发布的 slot id（如 `session-log-download`） | 会**替换**官方那一格；必须用自己的新 id |
| 规则存单个 `rules.json`（0.1–0.2 的做法） | 维护体验差：要转义、改一条重写整份、手滑一次整份失效（真实发生过的 0 字节事故）。0.3.0 改为「每条规则一个 txt + 单独的 state.json 只存开关」 |
| 面板里用 `<textarea>` 编辑规则 | 用户明确要求去掉；改为逐行 `<input>` 内联编辑，且规则正文本身就在独立 txt 里，面板只是辅助视图 |

> 历史记录：0.1.0 的设计文档曾把「客户端规则面板 UI」列为「需额外构建链，二期再说」。0.2.0 已实现，且实践证明**不需要构建链**（bundle 是普通 JS 文本，见 5.1）。
> 0.3.0 按用户反馈把存储从单 JSON 改为「每条规则一个 txt」，并补上插件页入口与 404 修复。
