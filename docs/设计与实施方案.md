# dialog-fence 设计与实施方案

> 对话「围栏」插件：给**每一次对话**设定边界与行为约束，规则可随时增删、下一轮即生效，且**不破坏前缀缓存、不膨胀上下文、不影响其它对话**。
> 本文档记录最终方案、每一条设计红线的源码级依据、以及被否决过的替代路线。

- 版本：0.9.0（0.1.0 = 宿主半边；0.2.0 = 追加浏览器面板 + 双形态安装；0.2.1 = 修正 `dsh.client.inject`、补真 React 渲染测试；0.3.0 = 每条规则独立 txt + 插件页 + 修复 404；0.4.0 = 设置左栏一级菜单 `settings.section` + 插件页卡片 `plugins.item`；0.5.0 = 改为按组合包安装（进「已安装」分组）+ 配置区迁到 `plugins.bundle.config` + 数据目录固定到 `<DSH_HOME>/dialog-fence/rules`；0.6.0 = 新增「通用规则层」（`rules/common/`，对每个对话生效），设置页主视图改为直接编辑围栏正文、不再罗列 sessionId；0.7.0 = 存储改为单个 `fence.json`（不再一条规则一个 txt）+ 围栏文件位置可自定义 + 设置页「打开文件夹」/「更改位置」按钮 + 修好会话头部面板与设置页不同步、徽标只数会话层的问题；0.8.0 = 「打开文件夹」不再静默失败：`spawn` 挂 `error` 监听、异步失败延后一轮报告（`openWarning`）、前端把 `opened`/`openReason`/`openWarning` 翻成一行可见提示，并显式 `windowsHide: false`；**0.9.0 = 规则编辑框从单行 `<input>` 改为多行 `<textarea>`：`Enter` 归还给换行、提交改用 `Ctrl/Cmd+Enter`，围栏文件路径框仍保持单行**）
- 落地日期：2026-10-20
- 代码：
  - `harness/dialog-fence/index.js`（宿主半边，零 import）
  - `harness/dialog-fence/client.js`（浏览器半边，手写懒 CJS 工厂，只 `require('react')`）
- 状态与数据（0.7.0 起是**单个 JSON 文件**，位置可自定义）：
  - `<围栏文件>` 默认 `<DSH_HOME>/dialog-fence/fence.json` —— 全部内容（`{"version":3,"enabled":bool,"rules":[string],"sessions":{<id>:{enabled,rules}}}`）
  - `<DSH_HOME>/dialog-fence/location.json` —— 位置指针 `{"file":"<绝对路径>"}`；删掉即回到默认位置
  - 优先级：`DIALOG_FENCE_FILE`（直接指定文件） > `location.json` > 默认路径；`DIALOG_FENCE_HOME` 可换基目录（测试用）
  - 0.3.0–0.6.x 的 `rules/common/*.txt` + `rules/sessions/<id>/*.txt` 仅在首次启动时被读取并迁移，老文件保留不删
- 挂载形态（0.5.0 主推）：作为 profile 组合包安装 —— profile `package.json` 的 `dependencies` + `dsh.profile.bundles` + 包内 `dsh.bundle.patch: ./cordis.patch.yml`；**不再**依赖 `<DSH_HOME>/profiles/<profile>/cordis.patch.yml` 里的 `file:///` 插入行（那条现在只是开发用备选形态）

## 1. 需求与红线（来自用户 CR-01）

| # | 要求 | 本方案的兑现方式 |
|---|---|---|
| 1 | 不影响 DSH Desktop 其它对话 | 规则分两层：**通用层**（`rules[]`）是用户显式开启的全局面板，**会话层**（`sessions.<id>.rules[]`）按 `sessionId` 分桶。两层都为空时渲染**空字符串**，而 `renderContextSections()` 会 `.filter(s => s.text.length > 0)` —— 空串 = 零 token、零注入、零副作用。装好但没配规则时，对任何对话都毫无影响 |
| 2 | 不破坏缓存命中 | 只注册 `systemPrompt.context()`（运行时上下文段），**绝不碰系统提示词段**；运行时快照由 agent-loop 以「纯追加一条 user 消息」落历史，已有请求前缀永不被重写 |
| 3 | 尽可能省上下文 | 快照文本不变时 `RuntimeContextProjection.project()` 直接 `return`（一条都不追加）；变了才追加一份新快照；渲染有 40 条 / 2400 字符硬上限 |
| 4 | 与已装的主动压缩插件 billion-context 共存 | 注入落在 `Current runtime context` 快照里 → 被其 `dshDurableToolPath` 归类为 `durable/runtime-context` → 自动进 `protectedLatestTools`，只保最新一份，旧快照照常被压缩 |
| 5（CR-03） | 每条规则单独一个 txt，不要 textarea | ~~存储从单个 `rules.json` 改为「`rules/common/` + `rules/sessions/<sessionId>/` 两层的 `NN-<slug>.txt`」目录；`state.json` 只存开关~~ **已被 CR-14 第 3 条推翻（0.7.0 合回单文件 `fence.json`）**；~~「不要 textarea」这一半仍然有效~~ **已被 CR-16 推翻（0.9.0 起规则正文改用 `<textarea>` 多行编辑）** |

| 9（CR-14） | 右上角「围栏」按钮点开后要**同步出现配置** | 见 5.5.5：`Panel()` 原来只渲染会话层，现在先渲染通用层再渲染会话层；徽标计数改为两层之和。根因是渲染分支不是数据流 |

## 2. 最终架构

```
五处界面（client.js）              /fence 命令（任意形态）      直接编辑 txt 文件
  conversation.session.header.utilities                     │
  + shell.overlay 浮层 + settings.section 设置页  │           │
  + settings.plugins.tab 标签页                    │           │
  + plugins.bundle.config（本包详情页配置区，key=包名）│        │
        │  fetch("api/dialog-fence")           │           │
        ▼                                      ▼           ▼
  host: connection.fetch.register   ctx.commands.register   fs
  { path:'/api/dialog-fence' }      { name:'fence' }         │
        └──────────────┬───────────────────┘                │
                       ▼                                     ▼
 <围栏文件>（默认 <DSH_HOME>/dialog-fence/fence.json；位置可由 location.json 指针或 DIALOG_FENCE_FILE 改）
   { version:3, enabled:bool, rules:[string], sessions:{<id>:{enabled,rules}} }
   ├── rules[]                （通用规则，每个对话都生效）
   └── sessions.<id>.rules[]  （会话规则，只对该会话生效）◀──────┘
                                   │
                     systemPrompt.context({name:'dialog-fence:rules', order:118})
                   │  通用规则为空 且 该会话没有启用专属规则 → 返回空串（零注入）
                   ▼
        systemPrompt.assemble({agent, scope:agent})
                                   │
                     renderContextSections() → 过滤空段
                                   ▼
        joinContextSections() ──▶ "Current runtime context. This snapshot supersedes ..." + 围栏段
                                   │
                RuntimeContextProjection.project(snapshot)
                    文本与上次相同 → return（零追加）
                    文本变化      → append 一条 user/message（surfaceOp: append）
                                   ▼
              会话历史（追加在已缓存前缀之后，不重写任何旧 token）
```

三条写入口（面板 / 命令 / 手改 JSON）最终都只落到同一个围栏文件，读路径唯一，因此不存在状态分叉。

### 为什么 0.7.0 又回到「单个 JSON 文件」

用户 CR-14 第 3 条明确要求：「不使用多个 txt 文件存储围栏的方式，使用单独文件，通过配置 JSON 内容的格式来配置围栏」。

0.3.0–0.6.x 用「一条规则一个 txt」解决了 0.1–0.2 单文件 JSON 的维护痛点（要转义、改一条重写整份、手滑一次整份失效——本项目真实发生过 `rules.json` 被写成 0 字节，见运维手册的事故记录）。0.7.0 的取舍变了：

- 规则现在**主要在界面里逐条编辑**（0.9.0 起是多行 `<textarea>`），用户几乎不手写文件；真要手写也是「整段 JSON 粘进去」，不是「改一行」。
- 「一条一个文件」带来的目录遍历、文件名前缀排序、`state.json` 与目录的双写一致性，全是额外复杂度。合并成一个文件后，**顺序就是数组顺序**，开关与正文同源，不存在两处状态。
- 数据量很小（每层上限 40 条 / 渲染总上限 2400 字符），单文件读写没有性能问题；写入仍是 `.tmp` + `rename` 原子替换，读失败只降级为「本轮零注入」且**不清空文件**，所以「写入半截 JSON」不再是致命事故。

迁移：首次启动时若老 `rules/common` / `rules/sessions` 目录存在，按文件名顺序读成 `rules[]`，按会话读成 `sessions.<id>.rules[]`，并沿用老 `state.json` 的开关；老文件原样保留不删。
**踩坑记录**：围栏文件已存在但**内容为空**、而老目录有内容时也必须迁移——0.7.0 首次实装就是「文件已存在就跳过」，导致 0.6.0 的 10 条通用规则一直没搬过来（`test/smoke.mjs` 用例 2b/2c 专门锁这两条：空文件要迁移、有数据绝不覆盖）。

语义细节：

| 操作 | 行为 |
|---|---|
| `rules[]` 非空 | 对**每一个**对话生效（包括全新对话），不需要任何开关登记 |
| `sessions.<id>.rules[]` 存在但没写 `enabled` | **自动视为启用**（否则手写 JSON 不生效，反直觉） |
| `sessions.<id>.enabled === false` | 以它为准（保留正文但不注入） |
| 顶层 `enabled:false` | 通用层与会话层一起静音，文件原封不动 |
| 空字符串 / 全空白 | 不算规则，跳过 |
| JSON 语法错误 | 不抛异常、**不改写文件**，本轮降级为零注入，控制台 warn 一条；修好即恢复 |
| 注入顺序 | 先 `rules[]` 的 1..N，再把该会话启用的专属规则接在后面连续编号 |

### 关键常量

| 常量 | 值 | 依据 |
|---|---|---|
| `CONTEXT_NAME` | `dialog-fence:rules` | 避免与内建段冲突 |
| `CONTEXT_ORDER` | `118` | 内建 `CONTEXT_ORDERS` 只有 `SANDBOX_POLICY:110` / `APPROVAL_POLICY:115` / `SUBAGENT_DELEGATION:120`；围栏属策略层，插在审批之后、委派之前 |
| `MAX_RULES` / `MAX_TOTAL_CHARS` | `40` / `2400` | 每层 40 条、渲染总上限 2400 字符，硬上限防规则膨胀吞上下文（超出渲染 `(fence truncated: N/M rules shown)`） |
| 单条规则长度上限 | `2000` 字符 | `/fence add` 与 API `add`/`update` 都校验 |
| `BASE_DIR` | `<DSH_HOME>/dialog-fence` | 由 `resolveDshHome()` 从插件所在目录向上找到同时含 `profiles/` 与 `sessions/` 的祖先；可由 `DIALOG_FENCE_HOME` 覆盖（测试与多实例用） |
| `FENCE_VERSION` | `3` | 围栏文件结构版本；读到更高的 version 也照常按已知字段解析 |
| 围栏文件 | `<BASE_DIR>/fence.json` | 0.7.0 起全部规则与开关都在这一个文件里；可由 `DIALOG_FENCE_FILE` 或 `<BASE_DIR>/location.json` 改到任意绝对路径 |
| `LOCATION_FILE` | `<BASE_DIR>/location.json` | 位置指针 `{"file":"<绝对路径>"}`；删掉即回到默认位置 |
| `LEGACY_DIR` | `DIALOG_FENCE_DIR` 或 `<BASE_DIR>/rules` | 只用于 0.3.0–0.6.x 多 txt 数据的一次性迁移，读完不删 |

### 为什么文本里绝不能出现 `{{ }}`

`dsh-system-prompt` 的 `interpolate()` 解析到未注册的 `{{name}}` 会**直接 throw**：
`unknown prompt variable "{{x}}" in context "dialog-fence:rules"`。
一次抛错就毁掉整轮装配 —— 所以插件里所有渲染路径都包在 `try/catch`，异常一律降级为空字符串。

## 3. 四条候选注入通道的对比（源码实证）

| 通道 | 缓存代价 | 存活能力 | 结论 |
|---|---|---|---|
| **A. `systemPrompt.context()`（本方案）** | 文本不变 = 0；变了 = 追加一条快照（1–2k token，纯追加不重写前缀） | `durable/runtime-context` 自动保护最新一份 | ✅ 采用 |
| B. 静态系统提示段（常量 section） | 0 | 系统提示词不受压缩 | ⚠️ 只能承载「永不变化」的底座文案；规则本体不能放（会变 → 见坑 1） |
| C. 动态系统提示段 / 动态 `PromptSection` | **破坏性** | — | ❌ 见坑 1 |
| D. `agent/pre-step` 追加普通 user 消息 | 纯追加，安全 | **普通 user 消息不在任何保护表里**，离开 `preserveRecentMessages:3` 窗口即被压缩吞掉 | ❌ 需手造消息对象且有被吞风险 |

### 坑 1（最重要）：动态系统提示词会废掉整条 KV 前缀

`dsh-agent-loop` 的 `SystemPromptProjection.project(rendered, input)`：

```js
if (!input.inHistory || input.startsSeries || rendered.length === 0) {
  const updates = nodes.slice(1).filter(n => n.text !== '').map(n => this.replace(n.seq, ''));
  if (head.text !== rendered) updates.push(this.replace(head.seq, rendered));   // ← 头部重写
  return updates;
}
if (latest.text === rendered) return [];
return [{ message: createSystemMessage(rendered), intent: { surfaceOp: 'append' } }];  // ← 仅 in-history 才追加
```

`inHistory` 只有在 provider 声明 `systemPromptUpdate: 'in-history'` 时为真。全库扫描 3245 个 `.js` 后确认：

- **`systemPromptUpdate` 的唯一赋值来源**是 `@deepseek-ai/dsh-llm-deepseek` 的 `DEFAULT_MODELS`（`deepseek-flash` 条目带 `systemPromptUpdate: 'in-history'`）。
- 本会话路由 **workbuddy**：0 命中。
- **opencode-go**（`dsh-opencode-go@*`，2.1 MB bundle）：0 命中。

⇒ 在这两条路由上，任何随时间变化的系统提示词段都会触发 head 重写、KV 前缀全废。**围栏规则是必然变化的，所以它绝对不能进系统提示词。**

### 坑 2：`agent/request` 瀑布不能用于注入

Host 契约原文：「Model-visible content must use logged channels; this waterfall cannot mutate messages.」，签名返回 `LlmCallConfig { provider, model, reasoningEffort?, temperature?, maxTokens?, stop? }` —— 没有 messages / system 字段。

### 坑 3：不要在注入文本里硬塞 `Current runtime context`

billion-context 的分类器按文本包含判定，且 `protectedLatestTools` 的 `collectLatestProtected()` 对同一虚拟路径**只保最后一条**。围栏若伪装成 runtime-context 就会和真正的快照抢同一条 `path`，而真正的快照更新更晚 → 围栏那条不是最新 → **不保护 → 被折叠**。本方案让围栏成为真快照的**一个段**，天然共享同一条路径，不存在抢夺。

### 坑 4：不存在的现成机制（避免重复投入）

- `billion-context` 的 `acp_rule` / `RULES_USAGE_PROMPT`：9 个 dist bundle 里各 1 次，只有定义无引用；`rulesEnabled` 的 5 个使用点全是 `...rulesActive ? [RULE_TOOL] : []`（只注入工具定义）；本会话 manifest 里也没有该工具。**规则回注系统提示词的那一环没实现。**
- `compress.rules: true`：**plugin 模式下 inert**（仅 proxy 模式生效），本机是 plugin 形态。
- `harness/fence/`：已被 PreToolUse 钩子（`guard.mjs`）占用，那是**工具执行**级拦阻，不碰对话内容；本插件刻意用不同目录名 `dialog-fence`。
- `$DSH_HOME/AGENTS.md`：本机不存在，属可用的零代码备选（走内建 agent-instructions，`Instructions from:` 标记 → `durable/agents-md`），但权威级别低于系统提示词。

## 4. 与 billion-context 的相互作用（实测数据）

本节数据来自本会话 `GET http://127.0.0.1:18820/__bili/plugin/status?conversationId=dsh&fallback=latest`：

- `pluginAgent: "dsh"` → `durableMessageToolPaths.dsh = dshDurableToolPath` 生效路径成立（`dsh-native.js` 主动发 `x-bili-plugin: dsh` 头）。
- 压缩日志会明确写出「下一个请求必然失效的前缀量」：
  `[acp-compress-obs] shrink N% (~X/Y tok) foldPoint=mNNNNN blocks=K anchor≈A tok ... postCtx≈P → next-request cache ceiling ≥C%`，其中 `C = floor(100 * anchorTok / postCtx)`，`anchorTok = Σ active.blocks(ceil(summary.length / 4))`。
- 实测本会话缓存命中率长期 **95%+**（如 `cached=21,333,760 / input=22,241,490`）。围栏段的稳定存在不改变这个比例，因为它属于「一次追加、长期不变」的快照文本。

若将来希望围栏**永不被压缩**（连旧快照也不折叠），在 `~/.config/billion-context/billion-context.json` 写：

```json
{ "compress": { "protectedTools": ["durable/*"] } }
```

`classifiesDurable()` 一旦看到 `durable/` 前缀，就不再自动追加 `durable/*` 到 `protectedLatestTools`，而是走 `protectedTools` 的**全历史硬排除**。代价是旧快照永不折叠、上下文单调增长 —— 默认**不建议**开启。

## 5. 可视化面板与双形态安装（0.2.0 新增）

### 5.1 为什么能做，且不需要构建链

DSH 的客户端插件机制（`@deepseek-ai/dsh-client-modules`）只做两件事：

1. `locatePkgJson(loaderName, baseUrl)` 找到插件入口文件**最近的** `package.json`；对 `file:///` 路径不校验包名。
2. 读该 `package.json` 的 `dsh.client`（要求 `platform === 'web'`），再用 `exports['./client']` 定位 bundle 文件。

组装时 `buildComboScript` 只是把每个 bundle 的源码用 `";\n"` 拼起来执行 —— **bundle 就是普通 JS 文本**，形态固定为：

```js
window.__ModuleLoader__.load({
  id: 'dsh-dialog-fence',
  factory: (require) => { /* 只 require('react') */ return module.exports }
});
```

所以 `client.js` 是手写的，没有 rollup/vite/esbuild 参与，`file:///` 挂载也能带 UI。

### 5.2 数据通道：`connection.fetch` 而不是 `webServer`

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `connection.fetch.register({path:'/api/dialog-fence'})` | 自带 Connection 层的 Host/Origin 检查与 token 鉴权 | 只能在有 `connection` 服务的形态（web / Desktop）用 | ✅ 采用，**用 `ctx.inject(['connection'], cb)` 等待就绪**，缺失时整段跳过 |
| `webServer.register({kind:'exact', path})` | 所有形态都有 | 需自己防伪造请求；`(kind,path)` 冲突直接 throw | ❌ 无必要风险 |
| `harness.handle` + `host.call` | 官方 RPC | 属 **cordis 沙箱插件运行器**（UI 里现场写的插件），loader 形态的包拿不到 `harness` | ❌ 形态不匹配 |

> **0.2.x 的 404 事故（已修复）**：最初写的是 `const connection = ctx.get('connection')`。
> cordis 的 `get(name, strict = true)` 在 `strict` 下**只返回 provider fiber 处于 ACTIVE(2) 的服务**，
> `_getImpl` 里是 `if (strict && impl.fiber.state !== 2) return;`。
> 若 dialog-fence 的 `apply()` 早于 `connection` 的 fiber 激活，就拿到 `undefined`，
> 整段 `connection.fetch.register` 被 `if` 静默跳过。
> 之后浏览器请求 `/api/dialog-fence`，`HostConnectionService.createSharedFetchHandler` 查
> `this.fetchRoutes.get(pathname)` 命不中、interceptor 也是 `undefined`，
> 于是返回 `new Response("not found", { status: 404 })` —— 与用户看到的左下角 `HTTP 404` 完全吻合。
> 官方范式（`dsh-web-app/lib/index.js`）也是 `ctx.inject(["connection"], cb)`，而不是 `ctx.get` 软取。
> 现在 `test/smoke.mjs` 会断言 `registered.injected === [['connection']]`，防止回归。

客户端用 **document-relative** 路径（`"/api/dialog-fence".slice(1)`），与 `dsh-session-log-export` 完全一致。

### 5.3 槽位选择

| Slot | 用途 | 为什么 |

> 为什么用 `settings.section` 而不是 `main` + `sidebar.panellist`：后者会在左侧多出一块**常驻主面板**
> （且 `main` 的 `replaceRisk` 是 `shadows-shipped-ui`，`keyDomain` 已占 `conversation`），
> 与「一个配置页」的诉求不符。

### 5.3.1 插件页与「开关」的两层含义（容易混淆，特此记录）

DSH 插件页里能看到的「开关」其实有两种，彼此独立：

1. **loader entry 开关**（`pluginManager.setPluginEnabled(entryId, enabled)`）：把整个插件进程停掉/启动。
   来自 `plugin_manager list_plugins` 的 `enabled` 字段。组合包形态下条目形如
   `{"entryId":"dsh-dialog-fence","moduleName":"dsh-dialog-fence","enabled":true,"fiberPhase":"active","patchId":"dialog-fence"}`
   —— 有 `patchId`、无 `readOnlyReason`，**可切**。（`file:///` 形态下 `moduleName` 是一整条路径，
   且 patch 层行不属于 profile bundle，所以那种形态不会出现在「已安装」清单里。）
2. **围栏业务开关**（本项目自定义）：围栏文件的顶层 `enabled`，控制「是否往上下文里注入规则」。
   插件仍然运行，`/fence` 命令与面板照样可用，只是不注入。

插件页本包详情页里的那一页管的是第 2 种（更贴近用户语义：关掉围栏 ≠ 卸载插件）；
第 1 种在本包详情页的行列表里，由 DSH 自己渲染。

### 5.3.2 插件页能否显示标题/描述/图标

组合包形态下 meta 来自 `ctx.get('pluginPackages').metaOf(name, base)` → `readPluginMeta(specifier, parentURL)`，
其第一行是 `if (barePackageName(specifier) === void 0) return void 0;`，而 `barePackageName`
对 `file:` / 绝对路径 / `.` 开头的 specifier 一律返回 `undefined`。
⇒ **`file:///` 插入行在插件页没有标题/描述/图标**；组合包插入行的 `name` 是裸包名 `dsh-dialog-fence`，
才会去 `node_modules/dsh-dialog-fence/package.json` 读 `name` / `description` / `icon`。
本包已加 `"icon": "./icon.svg"`，且 `iconOf()` 的约束（相对路径、`.svg/.png/.jpg/.jpeg/.webp`、必须在 manifest 目录内、≤256 KiB）全部满足。

| 形态 | 做法 | 依据 |
|---|---|---|
| **组合包（0.5.0 主推）** | 插件页「添加插件」填本包**绝对路径**（或 `dsh plugin --profile web add <绝对路径>`）→ Desktop 的 `profileBundlePackageBackend.install` 把源码**复制**进 `profiles/.generations/live/dsh-dialog-fence+<ver>+<hash>/`，pnpm add；`dsh-plugin-manager` 的 `reconcile()` 自动把包名 push 进 `dsh.profile.bundles` | `installGeneration` 源码：`sourceCopy = <staging>/source/<name>` → `installSpec = 'file:'+sourceCopy`；`inspectionOf` 只要 `dsh.bundle` 是对象就算 bundle |
| **`file:///` 挂载（开发用）** | `scripts/install.mjs` 往 `<DSH_HOME>/profiles/<profile>/cordis.patch.yml` 追加带标记的 `- insert:` 块（`name: "file:///.../index.js"`） | profile 补丁层是官方支持的最后一层，`patchReload: live`；但该行不属于 profile bundle，故不进「已安装」清单 |

> **两种形态互斥**，同时存在会有两条 loader 行重复注册槽位。切换前先卸掉另一种。

> **复制语义带来的开发流程变化**：本地路径安装不建软链，改 `harness/dialog-fence/` 里的源码
> 不会影响已安装的 generation 副本，必须卸载重装。这就是保留 `scripts/install.mjs`
> （`file:///` 引用形态）的原因——日常改代码用它，验证发布形态用组合包安装。

注意 `desktop` 这个 profile 名被 Electron 独占（`bin.js` 的 `rejectElectronProfile` 会直接 `program.error`）；本机 Desktop 实际使用的是 **`web`** profile。

### 5.5 两层规则、单文件存储与「直接编辑正文」（0.6.0 起，0.7.0 改为单文件）

用户 CR-12 的原话是「这个页面我需要能够直接配置围栏的具体内容，而不是展示 sessionsid，这个是没有意义的」。
问题不在渲染，而在**数据模型**：0.5.0 的配置页只能编辑「某个 sessionId 的规则」，
而设置页作为 root scope 的槽位**天然拿不到当前会话 id**（`settings.section` 的 ownerProps 只有 `{ close }`，
客户端也没有任何「当前会话」服务或事件，见 5.5.2）。于是它只能退化成一张 sessionId 表——对用户没有意义。

结论：给围栏加一层**与会话无关的通用规则**，让设置页有一个真正稳定、可编辑的编辑对象。

#### 5.5.1 两层数据模型

| 层 | 位置（0.7.0 起同一个文件里的两个数组） | 作用域 | 谁能编辑 |
|---|---|---|---|
| 通用层 | `rules[]` | **每个对话**都生效，包括新开的 | 设置页 / 插件详情页配置区 / 插件页标签页 / `/fence all ...` / 手改 JSON |
| 会话层 | `sessions.<id>.rules[]` | 只叠加到该会话 | 会话头部「围栏」浮层 / `/fence ...` / 手改 JSON |

注入顺序：先通用层 1..N，再会话层接在后面连续编号（`fenceTextFor()` 一次算完，仍受
`MAX_RULES` / `MAX_TOTAL_CHARS` 双限）。任一层为空则该层贡献 0；两层都空 → 返回空串 → 零注入。

宿主侧用一个访问器把两层抽象成同一种目标：

```js
function targetOf(scope, sessionId) { ... }   // { scope, sessionId, fence, rules, write(fence), enabled }
```

`applyAction(action, payload)` 用 `payload.scope === 'common'` 分流，通用层不需要 `sessionId`；
`handleApi` 的 GET 支持 `?scope=common`，POST 支持 `{scope:'common'}`。
通用层的开关复用顶层 `enabled`（这是自然语义：总开关本来就该管全局规则）。
`add` / `update` / `remove` 一律按**数组下标**寻址（0-based），不再有文件名。

#### 5.5.2 为什么不能「直接拿到当前会话」——已取证的死路

| 尝试 | 结果 |
|---|---|
| `cordis_inspect_query(client / Service / listService)` | 只有 `layout` / `locale` / `sessions` / `slots` / `theme` / `timer` / `uiWorkspace` / `workspaces`；`sessions` 的方法只有 `retain` / `using` / `retainInfo` / `refreshProjections` / `search` / `fork` / `scope(id)` / `binding(id)`——**没有「当前/选中会话」入口** |
| `Event / listEvents` | 只有 `connection/reset`、`locale/change`、`slots/changed`、`theme/change`，**没有会话切换事件** |
| asar 搜 `useSessionStatus` / `useActiveSession` / `activeSessionId` / `selectedSessionId` / `currentSession` | 命中的全是 `dsh-client-ui-conversation` 内部类字段（`SessionComposer.currentSession`）或类型声明表，**都不对外** |

唯一能拿到当前会话 id 的地方是 `conversation.session.header.utilities` 槽位（`standardProps` 里有
`sessionId: SessionId`）——但那正是会话头部那个「围栏」按钮。设置页拿不到。
所以「设置页直接编辑当前会话」在当时无解；正确的产品解是**通用规则层**。

#### 5.5.3 设置页的主视图（0.7.0 后）

`FencePage` 里没有 sessionId 表，卡片顺序：

1. 「对话围栏（dialog-fence）」：总开关 pill + 关/开按钮 + 一句说明 +
   **围栏文件路径** + `[打开文件夹]` + `[更改位置]`（点开后变一行绝对路径输入框 + `[迁移]`）。
2. 「围栏规则（对每个对话生效）」：`rules.map(RuleRow)`——逐条 `序号 + 正文 + [改][删]`，
   点「改」就地变**多行 `<textarea>`**（0.9.0 起；`Ctrl/Cmd+Enter` 保存 / `Esc` 取消）。
   底部一个多行编辑框新建，右侧「清空全部」，末尾 meta 行
   `注入 N 字符 ≈ M token · K/40 条 · 单条上限 2000 字符`。
3. 「某个对话的额外规则（可选）」：只有说明与「目前有 N 个对话设置过专属规则」，不列 id。
4. 「接入真实请求的唯一一段文本」：保留原有的 order 118 说明（解释为什么改规则不破坏缓存）。

会话专属那一层没有消失，只是**不在设置页展示**：会话头部浮层照旧，浮层顶部先列通用规则
（0.7.0 修复了「点开只有会话层、看不到刚配的通用规则」的同步缺陷，见 5.5.5）。

> 取舍：0.5.0 的会话表现在只剩「诊断价值」。用户明确说它「没有意义」，
> 所以删掉而不是折叠——真要查某会话的规则，`/fence status`、`/fence dir` 和文件系统都还在。

#### 5.5.4 围栏文件位置可自定义（0.7.0）

需求原文（CR-14 第 2 条）：「围栏里增加一个打开存储围栏的文件夹位置的按钮，并且要求可以自定义文件位置」。

- `[打开文件夹]` → `applyAction` 的 `openFolder`：Win32 `explorer.exe /select,<file>`（文件不存在则打开目录）、
  macOS `open -R`、其它 `xdg-open`，全部 `detached:true, stdio:'ignore'` + `unref()`，
  **绝不阻塞宿主**。测试用 `DIALOG_FENCE_NO_OPEN=1` 禁掉真实弹窗，返回 `{ok:true, opened:false, reason:'test-mode'}`。
- `[更改位置]` / `/fence file <绝对路径>` / API `setFile` → `moveFenceFile(target)`：
  校验必须是绝对路径、必须以 `.json` 结尾（目标是目录则自动补 `fence.json`）；
  目标不存在就把当前数据写过去，然后写 `<BASE_DIR>/location.json` 指针。
  **原文件不删**（用户可能只是换位置看，误删代价高）；删掉 `location.json` 即回到默认位置。
- 优先级：`DIALOG_FENCE_FILE`（环境变量，最高） > `location.json` > `<BASE_DIR>/fence.json`。

#### 5.5.5 修好「点开面板看不到刚配的规则」（0.7.0）

需求原文（CR-14 第 1 条）：「右上角的围栏按钮点开以后没有同步出现配置，需要修复」。

根因（0.6.0 代码实证，不是缓存问题）：`Panel()` 只渲染 `entryOf(sessionId).rules`，
而那是**会话层**；用户真正在配的是**通用层** `rules/common/`（当时 10 条）。
设置页改的是通用层，头部面板读的是会话层 ⇒ 面板里永远只有那条 SELFTEST，
徽标也只数会话层（显示「1」而不是「11」）。同一个 `refresh(sessionId)` 请求返回的
`snapshot` 里本来就有 `common: {rules}` 字段（0.6.0 已加），只是面板从来没用它。

修法（最小改动，不动数据模型）：`Panel()` 按「围栏规则（对每个对话生效）」+「仅本对话的额外规则」
两段渲染，徽标计数改为 `common.rules.length + session.rules.length`，
面板底的 meta 行同时显示两层合计的字符/token 数。

两段都是**可编辑**的（`RuleRow` 复用同一个组件）：通用段调用
`act(COMMON_SCOPE, 'update' | 'remove', { index })`（`COMMON_SCOPE = 'common'`，请求侧翻译成
`scope=common`），会话段调用 `act(sessionId, …)`。打开面板时会同时刷新
`refresh(sessionId)` + `refreshCommon()` + `refreshOverview()`，所以设置页刚改的内容
在浮层里立刻可见；两个入口写的是同一个 `fence.json`（见 client.js 的 `Panel()` 实现）。

**为什么不是「加一次刷新」**：`HeaderAction` 的 `useEffect(isOpen → refresh)` 一直是好的，
请求也成功；问题在渲染分支。所以修复点在组件而不是数据流 —— 这也是这条 bug 容易被误判成
「缓存/没刷新」的原因，特此记录。

#### 5.5.6 「打开文件夹」为什么看起来没反应（0.8.0）

需求原文（CR-15）：「点击打开文件夹没有反应，排查原因，顺便看一下围栏有没有真正注入进来且生效，并且不影响压缩」。

**两个独立缺陷叠加，缺一不可**：

1. **宿主半边说了谎。** `openFolder()` 无条件 `return { ok: true, opened: true, dir }`。
   `childProcess.spawn` 的失败是子进程对象上的 `'error'` **事件**，晚于函数返回，
   同步的 `try/catch` 永远抓不到；而且原代码连 `'error'` 监听都没挂，
   ENOENT 会变成未捕获的 `'error'` 事件（在 Node 里足以终止进程）。
2. **浏览器半边从不看结果。** `act()` 把 `openFolder` 的回包当普通概览
   `patch({ overview: snapshot })` 丢掉 —— 回包里的 `opened`、`openReason` 一个字段都没读，
   存储里也没有任何字段承载它。于是「成功」「失败」「被系统拦掉」在界面上完全一样。

**改法**：

- `openFolder()` 显式 `windowsHide: false`（实测：`windowsHide:true` 时 explorer 窗口
  `IsWindowVisible=false`、`style=0x4CF0000` 缺 `WS_VISIBLE`；`false`/不填时 `style=0x14CF0000` 可见。
  但插件源码里原本没有这个字段，所以这条只是加固，**不是已证实的根因**）；
  挂 `child.on('error')` 写入模块级 `lastOpenFailure`，**下一次调用时**作为 `warning` 报出。
- `applyAction()` 的 `openFolder` 分支把 `openWarning` 放进回包。
- 客户端 store 新增 `notice`，`noticeOf(snapshot)` 把三种情况翻成人话，设置页卡片 1 与浮层底部
  各渲染一行 `data-notice="open-folder"`。

**为什么「延后一轮报告」而不是同步报错**：`spawn` 是异步启动，函数必须立刻返回
（前端在等 HTTP 响应）。唯一可行的补偿是把错误存起来，下一次动作时带上。
这让「点了才知道上一次失败」成为可接受的代价 —— 比「永远显示成功」好得多。

**已知限制**：`explorer.exe /select,…` 的退出码恒为 1，不能当成功判据；插件能报的只是
「请求已发出」，无法确认窗口真的可见。因此文案是「已打开围栏文件夹」而非「已确认窗口出现」。

### 5.5.7 规则编辑框改用多行输入（0.9.0）

需求原文（CR-16）：「新增和修改围栏的输入框还是用 TextArea 这种吧吧，text 感官太差了，不好调整内容」。

这句话推翻了 0.3.0 的一条约束（CR-03 当时的「不要 textarea」）。当时的上下文是「一条规则一个 txt
文件、规则都很短」，单行 `<input>` 够用；到 0.7.0 之后规则正文已经是整句整段的中文
（现网 10 条里有 4 条超过 100 字符、最长 438 字节），单行框看不全、也不能换行 —— 用户判断变了。

改法（只动 `client.js` 的呈现层，宿主与数据格式不变）：

| 位置 | 0.8.0 | 0.9.0 |
|---|---|---|
| `RuleRow` 编辑态 | `<input class="dialog-fence-input">` | `<textarea class="dialog-fence-textarea" rows=3 spellCheck=false>` + 一行提示「Ctrl+Enter 保存 · Esc 取消 · 可换行」 |
| 浮层「新建通用规则」 | `<input>`，`Enter` 提交 | `<textarea rows=2>`，`Ctrl/Cmd+Enter` 提交 |
| 浮层「新建本对话规则」 | `<input>`，`Enter` 提交 | `<textarea rows=2>`，`Ctrl/Cmd+Enter` 提交 |
| 设置页「新建规则」 | `<input>`，`Enter` 提交 | `<textarea rows=3>`，`Ctrl/Cmd+Enter` 提交 |
| 围栏文件路径框 | `<input>` | **保持 `<input>`**（路径含换行没有意义） |

关键取舍：**`Enter` 必须归还给换行**。多行框里若还让裸 `Enter` 提交，用户就永远打不出第二行，
等于把「能换行」这个需求本身废掉。所以提交键改成 `Ctrl/Cmd+Enter`，并在框下直接写出这行提示
（不能指望用户猜）。`Esc` 依旧是取消。

样式：`.dialog-fence-textarea` 用 `min-height:66px` + `resize:vertical`（用户可以自己拉高），
`.dialog-fence-row[data-editing="true"]` 改为 `align-items:flex-start`，
并新增 `.dialog-fence-editor`（纵向 flex，包住 textarea 与提示行）与 `.dialog-fence-hint`。

宿主侧**无需任何改动**：`normalizeText()` 一直是 `value.replace(/\r\n?/g, '\n').trim()` ——
内部换行原样保留，只把 CRLF 归一成 LF。这条原本只是防御性写法，到 0.9.0 才成为契约，
所以 `test/smoke.mjs` 补了两个用例锁它：多行规则在 JSON 往返后逐行保留且仍带序号；
`甲\r\n乙` 渲染成 `1. 甲\n乙`。

## 7. 被否决的替代设计

| 方案 | 否决原因 |
|---|---|
| 规则放系统提示词 + 每轮更新 | workbuddy / opencode-go 未声明 `systemPromptUpdate:'in-history'` → head 重写、KV 前缀全废 |
| 复用 `acp_rule` 规则层 | 0.1.202 无回注实现；本会话未暴露该工具；plugin 模式 `compress.rules` inert |
| 靠 hook 桥（`UserPromptSubmit`）每轮注入 | 每轮一条新 user 消息，`updatedInput` 还不被 honor；成本高且不可控 |
| 把规则写进 `AGENTS.md` | 可行但全局生效，会污染其它对话（违反红线 1） |
| 用 `harness.handle` + `host.call` 做面板数据通道 | 那是 cordis 沙箱插件运行器的 API，loader 形态的包没有 `harness` 对象 |
| 用 `webServer.register` 暴露 API | 需自己防伪造请求；`connection.fetch` 免费自带鉴权 |
| 用 `ctx.get('connection')` 软取服务 | 默认 `strict=true` 只返回 ACTIVE 的 provider；`apply()` 时序早于 connection 激活就拿到 undefined，路由被静默跳过 → 面板 404。改用 `ctx.inject(['connection'], cb)` |
| 用 `plugins.item` 把卡片插到插件页 | **那个槽位的语义就是「官方分组里的官方插件卡片」**，改 id/order 都离不开官方分组。用户要求「放到已安装分组」⇒ 必须按组合包安装 + 用 `plugins.bundle.config` |
| 组合包安装后继续用包目录存规则 | 官方安装器把源码**复制**进 generation 快照，包目录每次升级都换；规则会随旧快照一起丢。改为 `resolveDshHome()` 向上找 DSH home，数据固定到 `<home>/dialog-fence/rules` |
| 复用已发布的 slot id（如 `session-log-download`） | 会**替换**官方那一格；必须用自己的新 id |
| 规则存单个 `rules.json`（0.1–0.2 的做法） | 维护体验差：要转义、改一条重写整份、手滑一次整份失效（真实发生过的 0 字节事故）。0.3.0 改为「每条规则一个 txt + 单独的 state.json 只存开关」。**0.7.0 又回到单文件 `fence.json`**，原因是规则主要在界面里逐条编辑、手写场景变成「整段 JSON 粘贴」，而目录遍历/前缀排序/双写一致性全是额外复杂度；写入仍是 `.tmp`+`rename` 原子替换，读失败只降级不清空，0 字节事故不再致命（见第 2 节） |
| 面板里用 `<textarea>` 编辑规则 | ~~用户明确要求去掉；改为逐行 `<input>` 内联编辑~~ **0.9.0 反转为用 `<textarea>`**（CR-16：单行框「感官太差，不好调整内容」）。0.3.0 当时规则短、单行够用；0.7.0 起正文是整句整段中文，单行既看不全也换不了行。记录在这里是因为它被推翻过两次，别再来回改 |
| 多行编辑框里仍然用裸 `Enter` 提交 | 那等于让用户永远打不出第二行，「能换行」的需求就自我抵消了。改为 `Enter` 换行、`Ctrl/Cmd+Enter` 提交，并在框下常驻提示 |
| 给 textarea 做「内容自增高」 | 要测量 `scrollHeight` 并回写 `style.height`，而 `renderToStaticMarkup` 下拿不到布局、测试会失真。改为固定 `rows` + `resize:vertical`，让用户自己拉 |
| 设置页继续以「sessionId → 规则」为主视图（0.5.0 的做法） | 用户 CR-12 判定「展示 sessionId 没有意义」。根因不在 UI：`settings.section` 是 root scope，拿不到当前会话 id，也不存在「当前会话」客户端服务/事件（见 5.5.2），所以那个视图天然只能是一张 id 表。0.6.0 改用与会话无关的**通用规则层**，让设置页有真正可编辑的对象 |
| 在设置页放一个「选会话」下拉框 | 同样要求用户理解 sessionId；且会话 id 对用户是随机 uuid，没有可读名称可显示（会话文件是 `session.v4.jsonl.zstd`，无明文标题）。不如把「每个对话都生效」作为设置页的语义 |
| 让用户用「选目录」对话框改围栏位置 | `input[type=file]` 传回的是**文件内容**或 `File` 对象，拿不到绝对路径；`webkitdirectory` 同样只给相对路径。Electron 的 `dialog.showOpenDialog` 在渲染进程里需要 IPC 通道（本包走的是 `connection.fetch` 规则，没有任意 IPC）。所以改为「一行绝对路径输入框 + `[迁移]`」，并把默认路径直接显示出来供复制 |
| 迁移时删掉老的多 txt 目录 | 迁移是一次性单向操作，删错了无法恢复；老文件体积小（几十 KB），保留成本远低于误删代价。所以迁移只读、不删，文档里写明可以手动清 |
| 「打开文件夹」只靠 `try/catch` 判失败（0.7.0 的做法） | `spawn` 的失败是异步 `'error'` 事件，晚于函数返回，同步 `try/catch` 永远抓不到；不监听还会让 ENOENT 变成未捕获事件。而且前端压根没读 `opened`。0.8.0 改为「挂 `error` 监听 + 存下失败 + 下一轮报告 + 前端展示」 |
| 「打开文件夹」失败时弹一个 alert/模态框 | 面板本身是浮层，再叠模态框对这类低风险动作过重；且宿主侧根本没能力确认窗口可见（`explorer` 退出码恒为 1）。改为在按钮下方渲染一行 `data-notice` 提示，可读、不阻塞、可重复点击 |
